## Config v2.1 Hierarchical Structure

As of Config v2.1, the compiler processes **hierarchical experiment directories** instead of flat config packs.

### Structure Overview

```
configs/default_curriculum/
├── experiment.yaml       # Experiment metadata
├── stratum.yaml          # Substrate configuration
├── environment.yaml      # Vocabulary (meters, affordances)
├── actions.yaml          # Action space
├── agent.yaml            # Network architecture
└── levels/               # Curriculum levels
    ├── L0_0_minimal/
    │   ├── curriculum.yaml
    │   ├── bars.yaml
    │   └── affordances.yaml
    ├── L1_full_observability/
    │   ├── curriculum.yaml
    │   ├── bars.yaml
    │   └── affordances.yaml
    └── ...
```

### Compilation Process

**OLD (v1.0 - flat structure)**:

```python
compiler = UniverseCompiler()
compiled = compiler.compile(Path("configs/L1_full_observability"))
```

**NEW (v2.1 - hierarchical structure)**:

```python
compiler = UniverseCompiler()
compiled = compiler.compile(
    experiment_dir=Path("configs/default_curriculum"),
    primary_level="L1_full_observability"
)
```

**Key Difference**: v2.1 compiles **ALL curriculum levels** in a single pass.

### Multi-Level Compilation

The compiler now:

1. Loads shared configs (experiment, stratum, environment, actions, agent)
2. Discovers all curriculum levels in `levels/` directory
3. Compiles EACH level through stages 2-6
4. Validates vocabulary consistency across all levels
5. Emits single `CompiledUniverse` with `all_levels` populated

**Benefits**:

- ✅ Cross-level validation (vocabulary consistency enforced)
- ✅ Runtime level switching (no recompilation needed)
- ✅ Transfer learning (checkpoints work across levels)

### Vocabulary Enforcement

**WHAT vs HOW Pattern**:

- **WHAT** (environment.yaml): Defines which meters and affordances exist
- **HOW** (bars.yaml, affordances.yaml): Defines how they behave

**Validation Rule**: All curriculum levels MUST have same vocabulary as environment.yaml.

```yaml
# environment.yaml (WHAT)
environment:
  meters:
    - name: energy
    - name: health

# levels/L1/bars.yaml (HOW)
bars:
  meters:
    - name: energy
      min_value: 0.0
      max_value: 100.0
      decay_rate: 0.5
    - name: health
      min_value: 0.0
      max_value: 100.0
      decay_rate: 0.1
```

If a level tries to add/remove a meter → **Compilation Error**.

### Support/Active Pattern

**Support** (stratum.yaml): Which observation fields CAN exist.

**Active** (curriculum.yaml): Which observation fields ARE active (vs masked).

```yaml
# stratum.yaml
stratum:
  vision_support: both  # Supports both global and partial

# levels/L1/curriculum.yaml
curriculum:
  active_vision: global  # Uses global, masks partial

# levels/L2/curriculum.yaml
curriculum:
  active_vision: partial  # Uses partial, masks global
```

**Result**: L1 and L2 have identical obs_dim (transfer learning enabled), but different active fields.
```

# Migrating to Config v2.1

**Status**: Config v2.1 is the ONLY supported config system. v1.0 flat configs are DELETED.

**Target Audience**: Future developers, AI agents reading this documentation

## Why v2.1?

**Problems with v1.0 (flat structure)**:

- ❌ **Vocabulary duplication**: Each level defined its own meters/affordances (inconsistent vocabulary)
- ❌ **No transfer learning**: Different obs_dim across levels (checkpoints incompatible)
- ❌ **Coupling**: Changing a meter required updating ALL config packs
- ❌ **No cross-level validation**: Vocabulary mismatches detected at runtime, not compile-time

**Benefits of v2.1 (hierarchical structure)**:

- ✅ **Single source of truth**: Vocabulary defined once in environment.yaml
- ✅ **Transfer learning**: Same obs_dim across levels (Support/Active pattern)
- ✅ **Separation of concerns**: WHAT (experiment) vs HOW (curriculum)
- ✅ **Cross-level validation**: Vocabulary consistency enforced at compile-time
- ✅ **Multi-level compilation**: Compile all levels in single pass

---

## Conversion Process

**There is NO automated conversion**. This is a pre-release project with zero users.

**If you have custom configs** (hypothetical):

1. Create experiment directory structure:
   ```bash
   mkdir -p configs/my_experiment/levels/my_level
   ```

2. Move shared configs to root:
   - Create `experiment.yaml` (new)
   - Create `stratum.yaml` (from old substrate.yaml)
   - Create `environment.yaml` (extract vocabulary from bars.yaml + affordances.yaml)
   - Create `actions.yaml` (new or copy from default_curriculum)
   - Create `agent.yaml` (new or copy from default_curriculum)

3. Move level-specific configs to `levels/my_level/`:
   - Create `curriculum.yaml` (metadata + substrate params)
   - Move `bars.yaml` (keep only parameters, remove vocabulary)
   - Move `affordances.yaml` (keep only parameters, remove vocabulary)

4. Validate:
   ```bash
   python -m townlet.compiler validate configs/my_experiment
   ```

## Troubleshooting

### Error: "Vocabulary mismatch"

**Cause**: Level's bars.yaml or affordances.yaml has different meters/affordances than environment.yaml.

**Fix**: Ensure all levels have EXACT same vocabulary as environment.yaml (name field must match).

### Error: "Missing levels/ directory"

**Cause**: Trying to compile v1.0 flat config with v2.1 compiler.

**Fix**: Use hierarchical structure (see Structure Comparison above).

### Error: "Primary level 'X' not found"

**Cause**: Specified primary_level doesn't exist in levels/ directory.

**Fix**: Check levels/ directory and use correct level name.

## Key Concepts

### WHAT vs HOW

- **WHAT** (environment.yaml): Defines vocabulary (which meters/affordances exist)
- **HOW** (bars.yaml, affordances.yaml): Defines behavior (decay rates, costs, etc.)

**Rule**: Vocabulary is a BREAKING CHANGE (all levels must update). Parameters are NON-BREAKING (per-level).

### Support vs Active

- **Support** (stratum.yaml): Which observation fields CAN exist
- **Active** (curriculum.yaml): Which observation fields ARE active (vs masked)

**Rule**: Support defines superset, Active selects subset. This enables transfer learning (same obs_dim, different active fields).

### Multi-Level Compilation

- Compiler processes ALL levels in single pass
- Validates vocabulary consistency across all levels
- Single `CompiledUniverse` with `all_levels` populated
- Can switch levels at runtime without recompiling
