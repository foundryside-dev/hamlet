## Decision 1: Cues Location

**Question**: Where do cues live in v2.1 structure?

**Decision**: **In `environment.yaml`** (vocabulary section)

**Rationale**: From reference config lines 360-383:
```yaml
# environment.yaml
cues:
  - name: low_energy_warning
    trigger:
      bar: energy
      threshold: 0.2
      direction: below
    display:
      icon: "⚠️"
      color: "#FF6B6B"
      message: "Energy critically low!"
```

**Implementation**:
- Cues are **NOT BREAKING** - they're UI metadata only
- Do NOT affect observations or obs_dim
- Purely for visualization hints

## Decision 2: Cascade Mapping

**Question**: How do cascades map from v2.1 to legacy EnvironmentConfig?

**Decision**: **Two-part structure**:
1. **environment.yaml**: Cascade graph structure (which→which relationships)
2. **levels/*/bars.yaml**: Cascade parameters (threshold, strength)

**From reference config**:

```yaml
# environment.yaml (STRUCTURE - vocabulary)
cascade_graph:
  - source: satiation
    target: health
    description: "Low hunger damages health"

# levels/L1/bars.yaml (PARAMETERS - behavior)
cascades:
  - source: satiation  # Must match cascade_graph
    target: health
    threshold: 0.3     # ← Curriculum parameter
    strength: 0.004    # ← Curriculum parameter (0.0 = disabled)
```

**Implementation**:
- Stage 2 builds cascade graph from `environment.yaml`
- Stage 3 merges parameters from `bars.yaml`
- Validation: All cascades from graph MUST appear in bars.yaml
- To disable: Set `strength: 0.0` (explicit, not omission)

## Decision 3: CompiledUniverse Output Type

**Question**: Multi-level or single-level CompiledUniverse?

**Decision**: **Multi-level** - Compile all levels, return single `CompiledUniverse` with multi-level support

**Rationale**:
- Enables cross-level validation (vocabulary consistency)
- Enables runtime level switching without recompilation
- Same cache for all levels (just select different level)
- Aligns with v2.1 hierarchical design

**Implementation**:
```python
@dataclass
class CompiledUniverse:
    # ... existing fields ...

    # Multi-level support
    experiment_dir: Path | None = None
    all_levels: Dict[str, LevelMetadata] | None = None

    def get_level(self, level_name: str) -> LevelMetadata:
        """Get metadata for a specific level."""
        ...
```

## Decision 4: Level Selection

**Question**: Compile all levels or on-demand?

**Decision**: **Compile all levels** in single `compile()` call

**Rationale**:
- Better for validation (vocabulary consistency across all levels)
- Same cache benefits (no duplicate compilation)
- Minimal overhead (5 levels × Stage 2-6 = ~500ms total)
- Aligns with cross-curriculum philosophy

**Implementation**:
```python
def compile(experiment_dir: Path, primary_level: str = None) -> CompiledUniverse:
    # Load all configs
    raw_configs = RawConfigsV21.from_experiment_dir(experiment_dir)

    # Compile ALL levels
    for level_name in raw_configs.levels:
        # Run stages 2-6 for this level
        ...

    # Return single CompiledUniverse with all_levels populated
    return CompiledUniverse(...)
```

## Decision 5: Substrate Behavioral Parameters

**Question**: Where do `boundary`, `distance_metric`, `observation_encoding` live?

**Decision**: **In `stratum.yaml`** under `substrate.grid`

**From reference config lines 73-97**:
```yaml
# stratum.yaml
substrate:
  type: grid
  grid:
    topology: square
    width: 8
    height: 8

    # Behavioral parameters (MANDATORY but NOT BREAKING)
    boundary: clamp  # clamp, wrap, bounce, sticky
    distance_metric: manhattan  # manhattan, euclidean, chebyshev
    observation_encoding: relative  # relative, scaled, absolute
```

**Rationale**:
- These are experiment-level settings (same across all curriculum levels)
- NOT BREAKING (don't affect obs_dim, only value ranges/behavior)
- MANDATORY (no defaults principle)

## Decision 6: Meter Range Semantics

**Question**: How do meter ranges work?

**Decision**: **Two-part structure**:
1. **environment.yaml**: Semantic range type (metadata for UI)
2. **levels/*/bars.yaml**: Actual bounds and initial values

**From reference config**:

```yaml
# environment.yaml (SEMANTIC - UI hint)
meters:
  - name: energy
    range_type: normalized  # normalized (0-1), integer (0-100), unbounded

# levels/L1/bars.yaml (ACTUAL - behavior)
meters:
  - name: energy
    initial: 1.0
    bounds:
      min: 0.0
      max: 1.0
      lethal_min: true
      lethal_max: false
```

**Rationale**:
- `range_type` is UI metadata (doesn't affect obs_dim)
- `bounds` control actual behavior (can vary by level)
- `initial` is curriculum parameter (different starting conditions)

## Decision 7: Modulation Graph

**Question**: How do bar→affordance modulations work?

**Decision**: **Same two-part pattern as cascades**:
1. **environment.yaml**: Modulation graph structure
2. **levels/*/affordances.yaml**: Modulation parameters

**From reference config lines 232-820**:

```yaml
# environment.yaml (STRUCTURE)
modulation_graph:
  - bar: energy
    affordances: [WORK]
    description: "Low energy reduces work effectiveness"

# levels/L1/affordances.yaml (PARAMETERS)
modulations:
  - bar: energy
    affordances: [WORK]
    type: linear_multiplier
    threshold: 0.3
    min_multiplier: 0.5  # At 0% energy, only 50% effective
```

## Decision 9: VFS Variables

**Question**: Where are VFS variables defined and how are they computed?

**Decision**: **Vocabulary in `environment.yaml`, computation in VFS system**

**From reference config lines 311-358**:

```yaml
# environment.yaml
variables:
  - name: deficit_energy
    type: scalar
    dims: 1
    scope: agent
    description: "How far below target energy"
    normalization:
      method: clip
      range: [0.0, 1.0]

  - name: time_since_last_eat
    type: scalar
    dims: 1
    scope: agent
    normalization:
      method: normalize
      range: [0.0, 100.0]
```

**Implementation**:
- Variables just declare "this field exists in observations"
- Computation logic lives in VFS compiler (separate from config)
- All curriculum levels see same VFS variables (vocabulary consistency)

## Decision 10: Support/Active Pattern

**Question**: How does Support/Active pattern work?

**Decision**: **Two-level control**:
1. **stratum.yaml**: Declares which fields CAN exist (support)
2. **curriculum.yaml**: Declares which fields ARE active (active)

**From reference config lines 100-143, 576-639**:

```yaml
# stratum.yaml (SUPPORT)
vision_support: both  # both, global, partial, none
  # both: grid_encoding + local_window (enables transfer)
  # global: grid_encoding only (power user optimization)

temporal_support: enabled  # enabled, disabled
  # enabled: time_sin, time_cos fields exist

# levels/L1/curriculum.yaml (ACTIVE)
active_vision: global  # global, partial
  # global: grid_encoding ACTIVE, local_window MASKED
  # partial: local_window ACTIVE, grid_encoding MASKED

active_temporal: false  # true, false
  # false: temporal fields MASKED (zeros)

vision_range: 0.5  # Used when active_vision: partial
day_length: null   # Used when active_temporal: true
```

**Validation**:
- If `vision_support: global`, only `active_vision: global` valid
- If `vision_support: both`, can choose `active_vision: global` or `partial`
- If `temporal_support: disabled`, must have `active_temporal: false`

## Implementation Implications

### RawConfigsV21 Structure

```python
@dataclass(frozen=True)
class RawConfigsV21:
    # Shared configs (WHAT exists)
    experiment: ExperimentConfig
    stratum: StratumConfig       # substrate + vision_support + temporal_support
    environment: EnvironmentConfig  # meters, affordances, cascades, modulations, VFS
    actions: ActionsConfig       # substrate_actions + custom_actions + labels
    agent: AgentConfig           # perception encoding + drive + brain

    # Curriculum levels (HOW things behave + what's ACTIVE)
    levels: Dict[str, CurriculumLevel]

    experiment_dir: Path
```

### Compiler Stages

**Stage 2** (Symbol Tables):
- Build from `environment.yaml` (meters, affordances, VFS vars)
- Build from `actions.yaml` (action vocabulary)
- Build cascade graph structure
- Build modulation graph structure

**Stage 3** (Resolve References):
- Merge cascade parameters from `bars.yaml`
- Merge modulation parameters from `affordances.yaml`
- Validate all cascades/modulations from graph are present

**Stage 4** (Cross-Validate):
- Check vocabulary consistency across levels
- Validate Support/Active pattern compliance
- Check enabled_actions subset of actions.yaml

**Stage 5** (Build Metadata):
- Build observation spec with `curriculum_active` flags
- Use `vision_support` + `active_vision` for masking
- Use `temporal_support` + `active_temporal` for masking

## Breaking vs Non-Breaking Summary

### BREAKING (affects obs_dim or action_dim):
- `substrate.type`, `substrate.grid.width/height`
- `vision_support` (adds/removes spatial fields)
- `temporal_support` (adds/removes temporal fields)
- Adding/removing meters, affordances, VFS variables
- Adding/removing actions

### NOT BREAKING (behavior only):
- `boundary`, `distance_metric`, `observation_encoding`
- `active_vision`, `active_temporal` (masking, not dimensions)
- `vision_range`, `day_length`
- All meter parameters (depletion, recovery, bounds)
- All cascade parameters (threshold, strength)
- All affordance parameters (costs, effects, hours)
- All training hyperparameters
- Drive configuration (reward function)
