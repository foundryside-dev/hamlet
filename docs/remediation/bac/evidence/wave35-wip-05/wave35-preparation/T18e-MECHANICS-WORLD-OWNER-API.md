## Healthy fixed-trace termination is not currently a named boundary

ENV public abandonment reasons are **only** `empty_participation` and `runtime_failure` (2298). Both authenticate current token and require active/active-awaiting-activation, aside from exact retained quarantined retry. Both end quarantined, not a healthy releasable checkpoint. Empty participation additionally requires no step_counts>0, activated owners and genuine owner-issued exact empty proofs from population/curiosity; it cannot apply after a real participating trace. Runtime failure does not mechanically verify a failure occurred, but labeling a healthy trace failure is semantically false and not an approved cleanup protocol. No capture-complete/healthy-stop/cancelled-trace reason or healthy discard/finalize method exists.

All-done changes agent liveness only; ENV does **not** automatically close/release or leave active on all-done. After a finite trace, whether rows remain live or all are done, ordinary close still requires genuine boundary work:

- prepare_episode_close(*,accepted,boundary_key,completion_content,participated_world_ids,dispositions) permits active/closed-awaiting-release/released-completed; it does not itself require all dones. Participants must exactly equal world IDs with actual step_counts>0, batch must match token; actual curiosity owner must issue prepared_dispositions with exact complete correlation/disposition roster. No outcome semantics or component producer is invented by ENV accepting completion_content:Any.
- freeze_episode_close authenticates current preparation/revision and moves boundary-pending. close_episode requires exact frozen preparation plus genuine curiosity committed dispositions with matching payload; stores actual completed history and moves closed-awaiting-release.
- authority.completed then requires actual completed boundary_effects from authority owner plus actual curriculum/exploration/population commit/epsilon install/selection sync role receipts, exact token/batch/content correlation and disposition identity. See T18e-COMPLETED-BOUNDARY-RECEIPT-API.md. It yields release; installation moves released-completed. No fake completion/native release is justified by reaching all-done or stopping a fixed number of steps.
- checkpoint_world_state accepts only explicit INITIAL/bootstrap-ready or COMPLETED/released-completed with genuine required history/closure provenance; no active or healthy partial-trace snapshot/export mode exists. Ordinary returned step observations/rewards/masks can be captured as outputs, but those data are not an authoritative closed world/native boundary.
