## Finite answer

**No check in the actual native prepared-handle installation notices a genuine bare manual Adam step between prepare and install. The same is true for a later native service update, model/moment edit or optimizer replacement.** Install checks only exact handle type, `prepared.owner is self`, and `not prepared.consumed`; it then consumes the handle and assigns `self.__dict__ = prepared.attributes`. The three actual install methods are RND903–907, adaptive328–332, ICM534–538. A same-owner manual step does not change native object identity or the handle's consumed bit. There is no native `validate_prepared`/commit-freshness API in these bodies.

This is source-proved absence of native freshness checking, not a runtime interleaving result or a confirmed violation of the existing delegated native contract. RND's reset docstring837–840 explicitly assigns construction/RNG to the enclosing owner and says the enclosing BANK authenticates freshness and boundary revisions. ICM485–486 likewise delegates RNG, boundary authority and final publication freshness. The controlling R0 design explicitly retains caller-owned same-object quiescence for standalone native prepare→install. No new native concurrency guarantee can be claimed from destination binding/single use.

**Native service steps are accounting-tracked, not native revision-tracked. Bare optimizer calls are not service-accounted.** These four bodies contain no lifecycle revision field, reset-generation token, thread Lock/RLock acquisition, active-operation guard or mutation interceptor. It would be inaccurate to say that owner-managed steps are revision-tracked while bare steps are not, based on these bodies. An outer owner may track managed calls in unread code; its producer must establish that separately.

## What validation can notice, and what it cannot

`validate_state(state)` is payload validation: RND735–737, adaptive271–272 and ICM382–383 call `prepare_state(state)` and discard the returned candidate. It is not `validate_prepared(handle)` and does not compare the prepared handle's expected-old live model against a newly mutated destination. It does inspect current destination configuration/schema/geometry to qualify the supplied payload; a later incompatible config/group mutation may therefore cause an incidental validation refusal. Such refusal is not a general freshness predicate.

- **RND/adaptive saved payload after a live manual step:** RND's `_prepare_available_state`656–664 deepcopies the now-live model/optimizer graph and loads the supplied saved model payload;665–708 validates/loads the supplied saved Adam payload. It checks shape/dtype/finite values, complete coherent moments and steps, and executes a disposable loaded probe711–723. These checks qualify payload and execution, not equality with current live weights/moments/S. `_prepare_state`783 compares prepared payload S to that payload's U-O+offset. Thus an unchanged coherent pre-step/reset payload can still validate after a live step. Adaptive repeats this through a copied inner RND at300–304. No freshness rejection is established.
- **RND/adaptive newly exported live state:** checkpoint_state551–582 computes signed `optimizer_step_offset = S-(U-O)` at574–576, using actual Adam S from599–602 (first state step; full payload validation subsequently requires agreeing steps705–706). A genuine coherent manual dense step changes actual model/moments/S and is represented by an increased signed offset while U remains unchanged. That is preserved supported behavior, not a stale-handle detector. Genuine history replacement may produce a negative offset; validation780–784 requires only integer offset and nonnegative resulting Adam clock plus payload consistency. This report neither removes that support nor claims a new execution of it.
- **ICM newly exported live state after an extra bare manual step:** ICM epoch_updates=U-O at430–435 is passed into `_optimizer_state`469. It requires the exact expected state-key occupancy348–351 and every supplied scalar step equal epoch_updates358–366. An ordinary extra step on the complete dense model while U/O stay unchanged therefore fails live-payload validation (empty-state expectation or mismatching step), subject to the stated genuine dense conditions. This is strict ICM accounting, not detection when installing the already prepared handle. ICM's model/moment geometry and finite checks319–377 do not compare live values with a captured fingerprint. **Do not claim a checkpoint-valid manually advanced ICM state.**
- **ICM old/reset payload validated after the live step:** current expected group configuration comes from self.optimizer at337–344, but ordinary Adam steps do not change those groups. Supplied model payload is checked/copied319–333, supplied moments/steps are checked against supplied counters335–379; no equality to current live S/model/moments is demanded. A coherent old/reset payload is therefore not made stale merely by the live manual step. Direct handle install bypasses even these payload checks.

## Disposition for B1/R0

Confirmed mechanism: native handles have no mutation freshness detector or lock, including for native-accounted managed service. Confirmed native contract: final owner freshness/quiescence is delegated. Confirmed consequence: absent external exclusion/checking, installing a prepared snapshot after an intervening mutation can overwrite that mutation and restore earlier conserved counters/queues. This is not labeled a newly confirmed accepted-contract defect in standalone native usage because that sequence violates its delegated quiescence premise. Whether any supported managed BANK/private/Q path exposes that sequence despite its required guarantee is a concrete outer-owner qualification gap, not proved here.
