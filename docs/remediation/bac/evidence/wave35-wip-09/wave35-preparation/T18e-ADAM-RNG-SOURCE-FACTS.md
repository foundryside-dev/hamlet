The actual reachable call graph is:

1. Base Optimizer construction creates empty instance step/state/load hook dictionaries and calls `_patch_step_function` (optimizer.py564). That patches the optimizer class's step once, using `profile_hook_step`; exact Adam class identity does not bypass this library wrapper.
2. The profile wrapper (optimizer.py511) enters `torch.autograd.profiler.record_function`; it executes global pre-hooks first, then instance pre-hooks. A pre-hook may replace `(args, kwargs)`, including the closure argument, or raise. It then invokes the wrapped Adam method. After successful return it calls `_optimizer_step_code` (a source-empty profiler entrypoint), instance post-hooks, then global post-hooks. Post-hooks are not a finally cleanup: an exception before them skips them. A post-hook can fail after the parameters have changed.
3. Adam.step is decorated with `_use_grad_for_differentiable` (optimizer.py59). This lazily imports `torch._dynamo`, records grad mode, sets grad mode from `self.defaults['differentiable']`, calls `torch._dynamo.graph_break()`, invokes the Adam body, then in finally calls graph_break and restores grad mode. These are real library boundaries even in the intended eager profile; no Dynamo/profiler implementation purity is proved by this capsule.
4. Adam.step (adam.py215) first invokes `_accelerator_graph_capture_health_check` (optimizer.py451), then optionally calls `closure()` under `torch.enable_grad()`. The closure return becomes the step return; no closure is called for the ordinary no-argument form. A closure may run arbitrary forward/backward/RNG work. Adam's body does not itself call a module forward or backward.
5. For each actual parameter group, `_init_group` (adam.py139) skips grad=None, rejects sparse gradients, and collects existing dense gradients. Empty state is initialized with scalar zero step and zeros_like moments (plus maximum moment for AMSGrad). The usual noncapturable/nonfused step is hosted on CPU. It invokes `adam(...)` defined in adam.py904, passing each group's real options and optional optimizer attributes grad_scale/found_inf.
6. Functional `adam` is decorated with `_disable_dynamo_if_unsupported` (optimizer.py106). Its wrapper uses compiler/state-step/device conditions to select the disabled fallback when needed; eager ordinary execution calls the function directly. `_compile.py28` shows the disabled wrapper lazily importing Dynamo and caching `torch._dynamo.disable(...)` when invoked. The underlying Dynamo implementations were not read.
7. Functional `adam` selects `_fused_adam`, `_multi_tensor_adam`, or `_single_tensor_adam`. `optim/_functional.py` only reexports this same `adam`; its separate sparse_adam is not called by ordinary Adam.step. No additional dense Adam algorithm is hidden in that reexport.
