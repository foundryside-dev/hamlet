## Item and inventory evidence

MAN105–122 defines ordinary dataclass world storage: `active` (ground and shared held items), `held` (lifted exclusive items), free rows and lifecycle maps. MAN330–333 validates the world and directly returns `self.worlds[world]`.

- MAN335–338 `items_in_world(world)` builds a new list from `state.active.values()` followed by `state.held.values()`, then returns `sorted(..., key=lambda item: item.vfs_index)`. It does not pop, insert, tick, normalize positions or invoke substrate/predicate/scheduler helpers. Arena-row order is explicit, independent of dictionary insertion order for distinct rows. Python's stable sort preserves concatenation order on ties at exactly fixed state; valid live instances have distinct allocated arena rows. MAN516–522 selects/removes a free row during explicit spawn, MAN535–552 stores it, and MAN583–585 moves exclusive items without freeing their row. Nothing in the read allocates a new arena row.
- MAN349–353 `holder_of(item)` obtains the item's world via MAN326–328 `world_of`, which reads `item.vfs_index` and calls REG71–77 `item_row_world(row, items_per_world) = row // items_per_world`. It filters holder IDs by MAN322–324 `world_of_agent(h) = h`, sorts the resulting IDs and returns the lowest same-world holder, or None. It does not take the first arbitrary set element, remove invalid holders, repair ownership, inspect inventory or call item lifecycle methods. With no holder, shared ground items and exclusive ground items both yield None. For valid carried items it consistently returns the same owner. This literal filtering behavior must be preserved.
- MAN177–182 creates its builtin InventoryState with one row per world and catalog `max_items_per_agent`. INV36–49 stores dimensions, a long tensor `slots[batch,max_items_per_agent]` initialized to -1, and an ordinary metadata dictionary. Reads of `slots`, `items` and their tensor/dictionary entries are ordinary stored-field accesses. INV115–129 `get_item` checks a slot bound and reads `.item()` without clearing the slot. INV131–137,144–146 fullness/count/membership checks also only read. Direct slot reads used by the public item assembly do not call `add_item`, `remove_item`, `reset` or `purge_instance`.
- INST10–31 is an ordinary dataclass: identity/type, position tuple, VFS row/profile, lifetime fields, exclusive flag and holder-ID set are stored fields, with no property or custom access hook. Merely reading position, vfs_index, instance_id, holders or lifetime cannot call INST33–36 `tick`. Even INST38–40 `is_expired` only compares the existing duration, but item enumeration does not call it. MAN705–723 explicitly performs lifecycle work through `tick`, which is a separate writer, not an observation getter.

The enumeration includes both active and held storage, so purity does not require dropping exclusive carried items. Shared held items remain active (MAN579–581). Hidden-versus-visible policy is not implemented by these getters: all live items are returned; the attributed ENV/publisher/substrate path supplies visibility. Neither hidden items nor carried items need be suppressed to establish this read proof. Position tuples and inventory slots remain live state; observation assembly must obey the unchanged-state requirement.

Manager construction/reseed, spawning, despawning and respawn scheduling can use randomness and mutate state (e.g. MAN287–307 owns per-world generators); these operations are not called by either named observation getter. Their existence is not evidence of read-time RNG consumption.

Registration/unregistration (REG858–878), row initialization (REG782–790), item writes (REG792–829), lifetime reset and restore are explicit writers. They are not invoked by the read accessors.
