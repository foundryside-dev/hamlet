## Current private stream fork and construction

Existing public API in world_curiosity_state.py:

- `WorldRNGState.create(*, descriptor, world_id, cuda_devices)` (542): creates fresh named streams from descriptor KDF seeds. This is fresh deterministic initialization, not a fork of an established owner's current continuation. Reusing it on every reset would restart streams.
- `rng.snapshot()` (640): requires quiescent, usable RNG coordination and healthy RNG owner; returns an owned `world-curiosity-rng-v1` value with descriptor stable identity, exact world_id, cuda_devices, and components. It captures the stored current named-stream continuations without entering an activation or advancing an owner revision.
- `WorldRNGState.from_snapshot(payload, *, descriptor, world_id, cuda_devices)` (579): validates/copies that payload and constructs a separate RNG owner. It validates exact named component set, original KDF seed labels, CPU Torch byte states, CUDA inventory/state, Python canonical state, PCG64 state, and legacy NumPy state. It restores continuation values, not just initial seeds. Inputs must be quiescent; used CUDA devices must already be initialized and explicitly declared. CPU ownership does not query/initialize CUDA.
- `rng.activate(component)` (689): installs that owner's named component into participating ambient globals, advances/captures it on exit, and restores previous ambient state. Returns activation-bound Python and NumPy sources. Same-owner nested different-component and A→B→A cases are supported; cross-owner nesting is rejected. Snapshot/from_snapshot cannot be nested inside an activation.
- `rng.validate_binding(*, descriptor, world_id, cuda_devices)` (663): identity validation without draws or stream capture, permitted in its own callback; it is not a fork/export operation.

Exact declared component names are `('model_init', 'target', 'predictor', 'service')`. Each component has a primary CPU Torch stream, Python stream, NumPy PCG64 generator continuation, legacy NumPy global stream, and declared CUDA continuations. KDF seed inputs exclude epoch, roster order/population and clocks; retaining continuation after reset does not require inventing an epoch-based KDF.

Exact activations visible in these four sources are model_init for construction and service for owned provider callbacks/snapshot/validation/load. They do not show actual make_backend/provider bodies: whether RND/ICM construction additionally enters target or predictor, and which streams it consumes there, are native/factory-owner facts. Do not claim that every declared component is consumed, or that only model_init is consumed. Run the actual factory with the supplied candidate RNG; preserve the entire resulting named-stream snapshot, including whichever components it actually advances.

`OwnedWorldBackend.construct(*, rng, factory)` (780) is public. Under the cooperating RNG guard and quiescence, it clones the supplied rng through snapshot/from_snapshot, activates the clone's model_init, calls `factory(candidate_rng)`, deep-clones the returned backend, validates checkpoint/load presence, and returns a new OwnedWorldBackend holding that candidate_rng. Thus it retains candidate construction draws in that owner's RNG rather than mutating the supplied RNG owner. Provider deep-copy policy reconstruction is part of the existing clone helper; actual provider/RNG internal binding still requires producer qualification. Do not bypass those native binding guards by separately rebinding arbitrary provider fields.

## Obtaining CURRENT actual-owner state is a distinct seam

`OwnedWorldBackend` has no existing public RNG-only fork/accessor or pure backend-clone exporter. Its actual RNG/backend are private `_rng`/`_backend`. The public operations available are construct, call, snapshot, prepare_restore and install.

`owner.snapshot()` (812) does export an owned envelope `{schema: 'owned-world-backend-v1', healthy, backend, rng}` whose rng comes from actual current owner continuation. However it first enters that owner's service activation to invoke native checkpoint_state; it increments owner revision even on success, and failure marks the owner failed. This is not a revision-neutral pure fork. Likewise `owner.call(operation)` (799) enters live service, increments revision and quarantines on any failed callback. Calling a nominally no-draw reset/clone operation through live `.call` still has those lifecycle effects. A native promise of no RNG draws does not erase these effects.

BANK `snapshot_world`/`checkpoint_state` also observe live providers and change BANK revision; they are transport/diagnostic operations, not a pure reset-preparation primitive. Existing CP `clone_provider(provider, *, family)` deep-copies an already accessible native provider with special policy reconstruction for count/ICM; it does not export the actual OwnedWorldBackend RNG and does not grant POP access to a private native object. CP `clone_native` transforms already validated transport for explicit shared→private initialization, not current stream custody or reset.

For preparation failure to leave live continuation and revisions unchanged, an additive owner-internal preparation helper must capture/fork current `_rng.snapshot()` and clone current native state under the existing guard/quiescence without live `.call`/`.snapshot`. This is a necessary new lifecycle seam, not an existing public API to tell POP to call. It must not expose a mutable live RNG owner or require POP to reach through BANK internals. N1's native API receives the actual fresh candidate from this BANK/owned lifecycle construction and performs no RNG draws itself.

## Retain fresh reset construction; discard disposable restore construction

These are two distinct, compatible phases:

1. Fork actual current private continuation off-side. Build the actual same-family fresh native candidate under candidate RNG custody. Capture the fully advanced candidate named streams after factory construction and before any publication. The fresh-learning reset result and that advanced RNG continuation belong together. Failures dispose of candidates; they do not rewind/reseed or publish live state.
2. Existing `owner.prepare_restore(payload, *, factory, validate_backend)` (830) may qualify an already assembled reset envelope. It forks payload.rng twice: saved_rng for installed continuation, work_rng for disposable factory/validation/load. It builds under work_rng.model_init, validates/loads under work_rng.service, checks validator purity and exact checkpoint transport, then returns PreparedWorldBackend containing the loaded candidate and saved_rng. Work_rng construction/validation draws are deliberately discarded.

Therefore prepare_restore is suitable after payload.rng already records the desired advanced reset construction continuation. It will preserve that saved continuation and discard only additional disposable reconstruction draws. Passing an unchanged current RNG payload and assuming prepare_restore's own fresh construction advances the installed stream is incorrect: it installs saved_rng from the input. Conversely, copying work_rng's accidental reconstruction advancement into saved_rng would make restore change the selected continuation.

The native reset method can use `fresh` learning/optimizer/statistics while retaining explicitly selected old pending obligations and accounting, but freshness of the native object does not independently select RNG semantics. All selected streams must be carried by the owner-produced envelope. Pure native reset qualification must not draw from ambient Torch/Python/NumPy streams.

## Prepared publication and failure authority

`PreparedWorldBackend` records destination token, destination revision, candidate backend, candidate RNG and used flag. `owner.install(prepared)` (869) requires correct owner token, unconsumed matching revision, non-None RNG, and quiescent RNG coordination. It publishes backend/RNG, clears failed flag for the explicit restore protocol, advances revision, and consumes/detaches the preparation. Do not manually construct a token to skip producer validation.

BANK separately owns `_restore_tokens`, BANK mutation_revision and opaque `PreparedCuriosityRestore`. `prepare_restore`/private initialization assemble runtime off-side and check BANK revision after parent correlation; `install_restore` (scoped_curiosity.py:1271) authenticates actual accepted authority when applicable, rechecks revision and replaces `self.__dict__` on the same BANK object. These are existing restore publication mechanisms, not proof that reset preparation or reset authority already exists. The new reset seam needs its own actual parent-boundary authorization and revision checks, preserving BANK/issuer/ENV identity and global RtEPS/cadence.

For normal candidate factory/validator/reset refusal with successful RNG cleanup, private activation restores ambient globals and the live RNG owner/backend/cursors remain untouched when no live callbacks/publication ran. Do not promise unconditional recovery: failed RNG capture/restoration marks RNG unusable/broken; restoration failure poisons the cooperating coordinator and participating operations fail closed. Existing live callback failure quarantines. Reset does not create a new midstep rollback or bypass those failure states.

## Shared custody: exact limit of owned-source evidence

BANK shared construction calls `_factory(None, None)` directly (scoped_curiosity.py:328), and `_factory` passes rng=None and descriptor=None into make_backend. Shared `_call` invokes the shared provider directly rather than OwnedWorldBackend. Shared restore uses CP.clone_provider(self._shared), validates/loads it and attaches gradients; the observed shared BANK transport has native/gradients but no parallel private RNG envelope. These four sources expose no actual shared reset RNG owner/snapshot/preparation interface.

CP `validate_archived_native` (curiosity_checkpoint.py:502) creates a disposable private RNG owner and activates model_init while constructing/qualifying an archived shared provider. That is ambient custody for this disposable validator, not evidence of a live shared RNG owner or shared stream ownership contract.

The world RNG guard explicitly says it coordinates participating lifecycle operations only; unrelated shared users are not excluded (world_curiosity_state.py:347). BANK's per-instance lock also does not exclude unrelated shared Torch/Python/NumPy/CUDA users. Do not claim private global swapping plus BANK lock gives process-wide shared quiescence.
