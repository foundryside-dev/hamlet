## Two concrete alternatives

**Stable existing-owner candidates:** current private/shared prepare_restore already performs genuine factory/validation/load offside and preserves ambient. However opaque candidates cannot be passed to CP.attach_gradients. Installing into the ORIGINAL existing owner before late BANK allocation/correlation would mutate it before the existing one-dictionary publication cut. Deferring that install would require a new candidate finalization/gradient-copy contract or a separately qualified all-child publication suffix. A live owner.call clone/gradient workaround also advances its revision/quarantines on error; it is not the pure current capture seam. Thus this alternative is not a demonstrated minimal adoption route for the actual current BANK topology. It remains a possible separately scoped architecture, not a capability to delete or a reason to expose candidate fields.

**Pre-registered offside replacements plus disposable validation:** actual core Shared.prepare_restore does not need the destination's live native backend: it uses its registered scope/device/revision and actual supplied factory, then validates/loads/clones before opaque issuance. Its ordinary restore install has no ambient continuation to stage. Factory-free registration can therefore precede the held lease; genuine bootstrap/load/install and CP's already-existing post-install gradient attachment can finish on the OFFSIDE owner under ambient preservation. No native ownership copy follows attachment. This retains BANK's one-dictionary original publication and requires no new gradient/inventory hook.

**Select the second mechanism for finite consumer reconciliation.** Three narrowly typed additive entrypoints suffice; they reuse actual _BackendOwner registration, _preserve_ambient and WorldRNGState._activate semantics inside the same WS body. ## Failures, partial work and poison

Invalid reservation state, duplicate bootstrap, wrong/expired/foreign lineage, bad binding or stale install refuses before native work/setters/publication at its applicable preflight. An ordinary factory/validator/load refusal before offside install, with successful ambient cleanup, leaves the original BANK/live owners and ambient unchanged. The reservation may return to empty healthy state for an explicit corrected attempt; unused handles from the failed aggregate must be stale/consumed/discarded rather than usable outside bootstrap.

A failure AFTER offside native installation/attachment may have changed the replacement. Quarantine/discard that OFFSIDE reservation; do not claim it unchanged or reset it through a public poison-healing API. The original BANK is still unpublished. A retry uses a new actual reservation while idle, allocation admission and genuine reauthentication. A late-world refusal similarly discards all unpublished replacement runtime; it must not leak partially installed original children.

Restoration/setter verification or declared-device completion failure poisons the actual common domain, preserves primary plus cleanup/completion errors and fails all participating shared/private entrypoints closed. Known ordinary refusal and unknown ambient cleanup are distinct. Weak cleanup/explicit unregister occurs only while idle; no membership mutation occurs inside the held preparation. Raw retained aliases still require caller-owned quiescence. All existing READY owner/manual/replacement behavior remains available.
