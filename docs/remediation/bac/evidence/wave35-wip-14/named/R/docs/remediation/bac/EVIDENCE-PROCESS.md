# BAC checkpoint evidence process

This document replaces the process text for the next reviewed checkpoint. It governs evidence publication and adds no acceptance waiver. Package qualification, independent application review, coverage, hardware, type, final CI and remote identity remain separate gates. Preserve prior artifacts, failures, backups, commits and registered worktrees.

## One authoritative record per candidate and check

1. Freeze the actual executed candidate: base commit, candidate tree, execution subtree identities and SHA-256 inventories for source, configs and protected artifacts. Keep its publication commit/tree as a separate identity. A later publication tree cannot stand in for the tree that ran.
2. For each candidate/check, maintain one authoritative check record with immutable attempts and an explicit terminal attempt. Preserve failed, interrupted, diagnostic, partial and unrun attempts and all retries. Each attempt identifies its own candidate manifest/tree, command or unrun reason, observed exit/counts or explicit unavailable reason, actual environment and hardware, controller/worker/child and import/thread/debug custody, raw logs and verifier. An absent timestamp or pytest count stays null with its reason. A later pass does not rewrite an earlier failure. Same-byte evidence reuse proves bytes, not execution of a newer source tree.
3. Seal a checkpoint receipt that binds the finite round interval, authoritative checks and terminal pointers, exact candidate, bounded component receipts, independent reviews, overlap-aware accounting, remaining failures and required next work. Do not sum nested selections or independent reruns as unique cases. Any change to a sealed receipt needs a new linked record; never replace old bytes.
4. Store each new artifact's exact bytes once. A reference identifies SHA-256, byte size, immutable repository path (or exact Git commit/path), and original producing path and role. Verify an existing target's path, size and hash before reuse. Preserve all logical aliases to one content object. A same-name file with different bytes is a distinct object. Snapshot approved CURRENT document bytes or bind them to exact commit/path and verified hash; a mutable path alone is insufficient.
5. Select only the explicit new interval and named additions. Do not recursively copy all wave35 history, mutable progress/task state, old source manifests or helper files. Include each changed required helper/verifier version and its dependency closure by name; reuse unchanged archived bytes by hash. Preserve every red/unrun/partial result inside the interval. Do not delete old duplicates as part of publication.
6. Root rehashes all selected inputs and reused targets immediately before copying, copies only new objects to previously nonexistent paths, verifies destination bytes, then writes the authoritative checkpoint manifest. Root checks independent qualification, candidate/execution subtree equivalence, approved review and document hashes, exact staged path scope and publication guards before its authorized Git action. If any selected byte or directory membership changes, reseal a fresh plan. Selector success is evidence integrity, never qualification or publication approval.
7. Publish a short status delta with the exact tested identity, named bounded result, retained failures and remaining gates, plus the next dependency. Link the immutable checkpoint and the one maintained evidence index. Append the new chain entry and update the index's current pointer without rewriting history. Refresh a full baseline inventory only when needed; later checkpoints link prior manifests and add new object records.

## Current finite WIP14 contract

The WIP14 selector is `W/evidence-management/bac_checkpoint_delta.py`, where `W=/workspace/hamlet/.superpowers/sdd/2026-11-01-bac-remediation-upgrades`. It takes a root-sealed terminal receipt with explicit terminal round, starting at R59, and no inferred final round. The receipt must represent the exact observed `Q/wave35-rN-*` top-level set for every N in R59–terminal, where `Q=/workspace/bac-review-2026-11-01/qualification`. It must semantically index every attempt by distinct check/attempt/record IDs and identify support artifacts. Several commands may share one top directory; each executed command then names its own distinct hash-bound structured result inside that directory, and the result is reconciled with its declared exit, counts and status when present. The top entry has `MIXED` status when its attempt statuses differ. Directory attempt inventories include every descendant file's path/size/hash and every descendant directory, including empty directories. The selector retains all files under those finite entries, including failed and unrun records, plus each R59–terminal candidate and fixture preflight, the terminal receipt, and named reviewed documents, component receipts, helpers, verifier and child witnesses.

Every attempt's candidate identity is independent of the terminal candidate. R64 shared-fixture, R67 owner-capture and intervening partial/diagnostic records remain bounded source-specific evidence; they do not qualify R72 BANK by reuse. An executed child names its actual attempt ID and source tree; a child required by a qualifying check must belong to that check's terminal attempt. A check declares its kind: runtime, static, collection, capture, preflight or diagnostic. A PASSED command requires actual exit zero and agreement with any structured result. Only a qualifying runtime claim requires positive pytest passed count, result/log references, positive recorded elapsed seconds and actual process custody. If absolute start/end timestamps were never recorded, both remain null with an explicit `absolute_time_unavailable_reason`; elapsed duration must agree with the raw structured result's `seconds` when present. Do not infer UTC times from file metadata. Single-process runtime records assert zero workers; xdist records supply exact worker witnesses. Static and collection commands can retain null pytest counts, missing exact timestamps and absent workers with explicit unavailable-custody reasons. A current FAILED global type result is included and remains FAILED; it does not prevent a bounded evidence plan from being integrity-ready.

The terminal receipt binds exact candidate and separately frozen qualification-subject bytes. Independent terminal review identifies reviewer and producer, evidence of their separation, bounded disposition and both reviewed subject hashes. The reviewed qualification subject is sealed before the receipt embeds the review hash, avoiding a circular hash. Root compares final receipt facts against that subject and independently verifies review custody. A component application review is not automatically a terminal receipt review; a tooling review is neither application qualification nor terminal receipt review. Unreviewed or changed document/review bytes stop final selection.

The selector builds an additive lookup from the baseline `inventory-v2.json` plus the exact hash-bound WIP13 manifest and selection-plan objects. It checks WIP13 predecessor and current-chain pointers, selected input hashes and sizes, each reused target's path/size/hash, normalized rooted paths, all ancestor symlinks, logical aliases and exclusive WIP14 destinations. This is targeted verification of selected reuse, not a fresh audit of the entire historical archive. New Python helper snapshots end `.py.txt`, with the original path/hash retained as provenance. Existing archived references keep their exact paths. No application source is imported or executed, and the tool makes no Git call.

A `--draft` plan is labelled `DRAFT PLAN ONLY` and cannot be assembled or published. A final plan labelled `READY FOR ROOT PUBLICATION CHECKS` certifies only the selector's finite membership, declared receipt relationships and checked bytes. It does not certify the truth or completeness of independently authored semantic custody, source execution, whole-package acceptance, remote publication or CI. A final receipt must not be manufactured from draft unknowns to obtain this status.

It never stages, commits, pushes, writes the authoritative WIP14 manifest or edits process/index/chain/AGENTS.

Verify the exact remote identity and CI independently after publication. Assembly success alone is not a sealable navigation delta; a partial assembly is never reusable as successful publication.
