**SPEC: CHANGES REQUIRED. QUALITY: CHANGES REQUIRED.** The additive design correctly identifies the present core gap: empty membership is not CUDA enrollment; current `register` needs initialized exact indices under idle domain custody; current nested/outer operation completion uses full declared member sets; and domain-before-owner exclusion must extend through CUDA completion. Its proposed idle gate, same-participant union, operation completion subsets, and direct dynamic selection are plausible *new* contracts, not existing APIs or GPU evidence. The following finite findings prevent approval as written.

1. **S1 — Defaulted `operation` argument conflicts with the repository's no-defaults/static contract and stated zero-compatibility rule.** The design says to extend `domain.operation` with an optional `cuda_devices` argument and make omission retain full-member behavior. The current public signature requires `participant`, `operation_kind`, `lineage` and has no defaulted device argument. An omission-preserving default would add a forbidden default/compatibility path and risks another ratchet increase; a whitelist or guard suppression is not a repair. Settle an explicit required caller migration or a genuinely separate public API, with typed signatures and coherent existing BANK/core call updates in their own bounded packets. This finding does not require removing any supported replay device behavior.

2. **S2 — The post-poison local gate may initiate CUDA before that work is proven ambient-free.** `local_cuda_access()` is allowed while the common domain is poisoned and the design says it may lazily initialize/resolve CUDA for local deterministic work. The design itself says PyTorch initialization's RNG side effects are unproven. Initializing a new CUDA runtime under common poison therefore cannot yet be classified as permitted owner-local scratch/data work; it could affect ambient continuation while ordinary domain admission is forbidden. Restrict the proposed post-poison guarantee to individually established ambient-free operations and already-qualified initialization state, or supply the exact Torch/runtime evidence before permitting initialization there. Keep healthy CPU owner-local work and the previously accepted disposable scratch-generator category. The public current domain has no `local_cuda_access` or poison-bypass initialization authority.

3. **S3 — A local CUDA mutation does not stale a core current token by itself.** The design's causal-test list says a local mutation between same-parent prepare/install stales the candidate by existing currency/revision rules. Source-exact core `current_token`/`validate_current` sees domain generation, revision and ordinary-work currency. The proposed `local_cuda_access` grants no `RNGOperation`; its ordinary successful mutation does not advance those core fields. While a parent lease stays held, domain revision also stays unchanged. Therefore this test needs the replay producer's actual owner revision/material/content invalidation to be specified and checked at final install. A local gate or no-op resolution cannot be treated as a core token invalidator. If initialization or enrollment occurs, their separately proposed currency/generation changes can stale a token; this does not cover general local mutations.

4. **Q1 — The idle initialization failure cut needs a concrete owner-visible state rule.** `admission` may call `torch.cuda.init()` before any `RNGOperation`, then validate an explicit index and enroll while the replay owner lock is held. The design proposes a gate failure-report mechanism and conservative poison for failed initialization, but must specify which gate has that method, whether successful initialization followed by invalid index/collection refusal has already invalidated preparations, and how the original error and cleanup/completion error are retained. An invalid index discovered *after* successful initialization is not a pre-attempt no-effect refusal, even if replay storage is unchanged. This is a finite API/error-order contract, not a reason to invent rollback of CUDA initialization. Current core `poison(operation=..., error=...)` requires an authentic active operation and cannot serve this pre-operation cut.

5. **Q2 — Cross-owner lock order and lifetime must be explicit in the new parent preflight contract.** The design's preflight holds the domain gate and replay owner lock while the parent opens its operation, and requires the nested replay call to reenter that owner lock. This is safe only when the parent has not already taken a parent/BANK/ENV lock before gate entry, when the replay lock is intentionally reentrant for that same thread, and when the actual weakly registered replay lifetime owner remains pinned across gate, parent lease and device completion. Record these conditions in the public preflight API and test the actual nesting path. The current core operation pins an admitted participant, but the proposed gate before the nested replay operation must itself retain the needed replay owner lifetime. A new nested protocol's declared target inventory is a valid prospective condition; it is not evidence that an old supported dynamic/lazy path may be removed.

## Bounded preserved conditions and disposition

The design's exact completion-set distinction is needed: nested completion must use the selected subset and the outer operation's accumulated union, while existing consumers' full-member behavior needs an explicit nondefault migration decision under S1. Membership expansion must keep the same participant/weak owner/entrypoint identity, increment generation only for a real union change and require truly idle custody. A no-op resolution/enrollment must not accidentally refresh or stale a held prepared handle; an ordinary admitted nested call still stales it by core currency as documented in `T18e-R0-DOMAIN-NESTED-TOKEN-API.md`. Completion failure must remain inside replay owner exclusion, poison common custody and quarantine uncertain replay publication. These are required review criteria for the new API, not verified implementation facts.

Direct `torch.device("cuda")` and `cuda:N` empty construction and first-use lazy behavior remain required; direct dynamic unindexed resolution must continue per actual operation. The proposed declared inventory for a **new** nested parent preflight does not establish old capability removal. Applicable multi-device/asynchronous CUDA qualification remains owed. Actual five-body proposed design inventory is 4464 production lines with no test body; its own later slices must remeasure complete bodies and test growth under five/5000. CPU B1/B2/B4/B5 repair proceeds first, and no B6 approval or programme accounting change follows from this prose design.
