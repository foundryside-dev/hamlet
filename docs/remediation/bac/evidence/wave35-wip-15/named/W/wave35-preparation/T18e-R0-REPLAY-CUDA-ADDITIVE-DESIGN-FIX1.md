## S1: a distinct explicit-subset operation API

Do **not** add an argument or default to existing `domain.operation`. Keep its present required signature and full-member completion semantics intact. Add the distinct typed public operation:

`domain.device_operation(*, participant: RNGParticipant, operation_kind: str, lineage: RNGOperation | None, cuda_devices: tuple[int, ...]) -> Iterator[RNGOperation]` (context-manager API).

Every argument is required. This API's meaningful additional contract is exact per-invocation device accounting: authenticate the participant and lineage; require the supplied exact/sorted/unique tuple to be a subset of initialized enrolled membership; complete that tuple at this nested exit and add it to the authentic outer operation's accumulated union. It has precisely the existing operation's admission, participant pinning, kind/currency, revision, token and failure rules. It is not a wrapper that conditionally omits a new parameter, an overload providing omission compatibility, or a whitelist exemption. Existing `operation` means full declared-member completion; `device_operation` means explicitly bounded invocation completion. Both can use one internal implementation with an explicit already-selected completion tuple and no default.

All replay domain-admitted sample/prepare/install paths migrate explicitly to `device_operation`; their CPU paths supply `()`. Existing BANK/core clients remain genuine full-member clients of the unchanged `operation`, so this proposal requires no fictitious migration to preserve their signature. A future client choosing subset semantics must migrate explicitly in its own bounded packet and prove its inventory. Test mixed nesting in both directions: a full-member parent with a subset replay child, and a subset outer operation with a full-member nested participant. The outer union must include exactly each participating scope's required devices.

## S2: post-poison local work excludes CUDA bootstrap

Replace the initial local gate's unconditional initialization permission. `domain.local_cuda_access()` is a synchronization gate for a finite producer-owned set of proven ambient-free operations. It is never RNG admission or authority to draw, prepare, install, register or enroll. Admission through it is not itself evidence that a method is ambient-free.

Healthy idle custody may initialize for a local tensor path under the explicit bootstrap state machine below, before any owner lock. An active parent may not initialize. **Commonly poisoned custody may not initiate CUDA initialization, qualify a previously unknown runtime, or run an unproven local leaf.** It may only execute an individually established ambient-free leaf whose CUDA runtime readiness was already established under healthy custody, using actual initialized indices. Keep a process-local READY fact established by successful healthy bootstrap or healthy verification of an already initialized runtime; it is not a future device enrollment and cannot be fabricated by `status()`.

For an already READY runtime, unindexed selection is re-resolved with the initialized-runtime current-device query; it is not pinned to a previously selected index. That query and the leaf's actual tensor/scratch path must be covered by the explicit ambient-free classification and supplier contract. If the selected path cannot satisfy that contract, refuse that local CUDA path before effects. Do not speculate that unproven initialization was previously permitted after poison. No user approval is sought for withholding a capability never established by the accepted rule.

CPU owner-local leaves and the accepted disposable-cloned-generator scratch category retain their existing owner-only exclusion and local revision discipline after common poison. They do not enter the new CUDA gate or access CUDA attributes. A CUDA-using local path is recognized from both destination and actual supported tensor inputs; a CPU destination with GPU input is not a CPU-only leaf. Completion failure on an admitted local CUDA leaf still reports poison through its authentic live gate and quarantines the affected owner; ordinary success does not heal poison or turn into ambient admission.

## S3: owner mutation currentness is producer-owned

A successful ordinary local CUDA gate does not advance domain revision/currency/generation. Neither does a no-op resolution or no-op enrollment. Explicit initialization and actual membership expansion have only their separately defined lifecycle effects. Do not use local gate entry as a substitute token invalidator.

Every replay-owner mutation, including local clear/store/priority/configuration changes in the accepted mutation set, increments the producer's `_replay_revision` under `_replay_lock` before executing its mutation body, as current `_owner_operation(mutation=True)` does. An attempted mutation that then raises conservatively leaves that owner revision advanced. Internal helper nesting may advance it more than once under today's semantics; never decrement/reset it or depend on an exact increment count. Pure local reads do not advance it. Publication retains its existing revision/quarantine/one-use discipline.

Each prepared handle records issuer-owned material, the actual owner revision and its authentic core token. After copying/staging and immediately before first publication assignment, installation checks both unchanged owner revision/material authority and `domain.validate_current` on the original token. A local mutation between same-parent prepare/install must fail the **owner revision** comparison even if the core token would still validate. The causal test separately demonstrates that unchanged core fields do not rescue the stale owner candidate. A same-parent admitted sibling ordinary operation tests core currency invalidation independently; initialization/enrollment invalidation has its own tests. Retain B1 destination/content validation and B2 issuer-held material; this delta cannot replace either with a freshly issued core token.

## Q1: bootstrap ordering, states and failure ownership

Both proposed live gate types (`RNGAdmission` and the distinct local CUDA gate) expose the same narrow authenticated `report_failure(*, error: BaseException) -> None` method for uncertain CUDA bootstrap/completion. It authenticates issuing thread, open gate, PID and sole-domain ownership, and retains the first common poison cause. It requires no fabricated RNGOperation. It does not grant publication/admission authority, erase earlier errors or clear poison. In an already active real operation its failure is also propagated through that operation's established exit aggregation. Expired/copied/wrong-thread gates refuse.

Bootstrap runs before acquiring replay owner exclusion. Resolve structural device validity first without CUDA work; an already-established initialized runtime may validate explicit bounds before any attempt. For a not-yet-established runtime, use this state sequence under exclusive idle domain custody:

1. **UNCHECKED:** validate supported device syntax and bootstrap eligibility. Poisoned, active-parent or reentrant bootstrap requests refuse without calling `cuda.init`. No owner data changes.
2. **VERIFY/READY:** if healthy inspection establishes CUDA already initialized, validate count and selected index and record READY without initializing or advancing lifecycle currency. Verification is not allowed to claim a successful init that did not occur. A valid already-READY no-op query preserves preparations. A normal out-of-range index refuses without poison or membership change.
3. **ATTEMPTING:** when actual initialization is necessary, advance the domain's ordinary-work currency once immediately before `torch.cuda.init()`. Do not increment revision as if an RNGOperation had exited; no operation exists. This is an explicit lifecycle invalidation of all earlier core tokens, including an attempt that later fails. Guard against same-thread bootstrap/registration/operation reentry during the attempt.
4. **INITIALIZED:** after init returns successfully and initialized state is verified, record READY. Then validate the reported count and explicit or selected index. Normal invalid-index refusal now leaves READY and the currency invalidation in place. Do not roll back runtime initialization, restore token authority, enroll an invalid index or claim this was a pre-attempt no-effect refusal. Replay storage/revision remains unchanged because no owner lock/body has yet run.
5. **ENROLLED:** after successful resolution, acquire owner lock, validate local health, inventory actual supported storage/inputs/material, and perform idle union enrollment. A real set expansion changes membership generation once. Inventory/argument/owner-health refusal after successful initialization leaves READY and the prior lifecycle invalidation; it neither publishes replay storage nor poisons merely for a normal refusal. Any already committed membership change remains visible and invalidates tokens; no compensating generation reset.

A failed init attempt or unexpected CUDA-runtime verification/cleanup failure has no proven clean rollback: report it through the live gate, leave readiness unavailable/uncertain as applicable, retain currency invalidation and refuse future ambient admission through common poison. If no owner storage/publication was touched, do not claim owner publication corruption or require a fabricated owner quarantine; common poison suffices. A specifically proven clean no-effect initialization failure class could later be added by supplier evidence, but none is assumed here.

Error aggregation is explicit. Keep the original bootstrap/body error as primary. Attempt only cleanup/completion justified for known touched devices; never sweep every available device to discover safety. If such cleanup/completion also fails, retain each distinct exception in a BaseExceptionGroup with the primary first, and report the first uncertainty cause without overwriting existing poison. If there is just the primary, re-raise it. A normal invalid-index or inventory refusal after successful verified initialization has no known tensor work to complete and no invented rollback. A CUDA query failure is not relabeled as normal invalid-index rejection. After real replay tensor work starts, the initial design's completion-under-owner rule and quarantine-on-uncertainty rule apply.

## Q2: preflight ordering, pinning and finite reentry

The public replay preflight context is synchronous and same-thread. It must be entered before the caller acquires any parent/BANK/ENV or other cooperating owner lock. Hold no such locks across preflight entry; no await, task handoff or yield to another execution owner is permitted. The ordering for the new integration is sole domain gate -> deterministically ordered replay-owner locks -> any parent lifecycle locks acquired inside its operation. Parent/BANK/ENV owners must confirm their real call sites fit that order in their bounded migration packet; a caller already holding a parent owner lock must move preflight outward, not acquire domain custody from there.

The shared multi-replay preflight helper acquires one domain gate and all requested replay locks in a stable total order before parent entry. A single-replay preflight is the singleton form. Do not compose independent cross-owner preflight calls after taking the first owner lock. Nested operations on an owner already included in preflight intentionally reacquire that same `RLock` on the same thread. New owner-lock acquisition outside the declared plan while holding those locks is not supported by this parent protocol; include that owner at outer preflight. This is prospective parent API discipline, not a claimed removal of a historical replay route.

On entry, the preflight implementation resolves each authentic participant's weak owner under the actual domain gate and holds a **strong reference to that exact lifetime replay owner** before lock acquisition. Keep those references, gate and replay RLocks alive through initialization/enrollment, parent operation body, nested replay scopes and parent completion. Finally exit the parent operation, release replay locks in reverse order, then release owner pins/domain gate. Failure paths use the same order. Pin release cannot precede the last device completion. The ordinary operation's own pins remain normal independent protection once the replay participant enters it; they do not replace the preflight pins before that point.

The shared replay dispatcher tracks a private issuing-thread scope only to reuse already acquired gate/owner exclusion for producer-internal local helper nesting. It does not infer lineage for a public sample/prepare/install. Such public calls still require their explicit authentic lineage and enter a real `device_operation`; None under a parent refuses. Do not let an internal local-scope marker admit an unrelated public callback or skip currentness. Unrelated same-owner lifecycle reentry during staging/publication remains refused; only declared producer-internal helper calls and the intended sequential nested prepare/install are allowed. No domain acquisition begins from an independently held owner-only lock: tensor-using entrypoints dispatch to their gate before owner acquisition; owner-only metadata leaves must not call back into gate-requiring entrypoints.
