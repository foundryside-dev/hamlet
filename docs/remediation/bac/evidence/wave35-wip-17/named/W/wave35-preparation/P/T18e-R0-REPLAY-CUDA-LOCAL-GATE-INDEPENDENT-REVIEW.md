## Blocking finite finding: contract-to-participant authorization

The proposed `local_cuda_access(*, participant, contract)` authenticates a real registered participant and a source-issued `LocalCUDAContract` identity, but the text does not require the core to authenticate that **this participant's owner is authorized for this contract's exact producer path**. A valid participant from another producer could present an exported replay contract constant. Checking each identity independently would admit a mismatched owner/path even though the manifest names an audited replay leaf. The current core `operation` prevents this analogous mismatch by checking `operation_kind` against that participant's own registered `entrypoints`; the proposed local gate needs an equally explicit relation. This is not a request for arbitrary caller purity detection or stack reflection: the contract can remain cooperative for actual tensor/input behavior while the core enforces its own issuer/owner binding.

**Concrete fix:** specify, in the core-owned immutable manifest/issuance protocol, the permitted producer owner identity/class or registered membership route for each contract, and make `local_cuda_access` reject a contract/participant mismatch before `resolve_cuda`, owner work or completion scope. Clarify where the named production identities are issued and how a later bounded replay producer packet enables them without a public caller registration/boolean/string escape hatch. A core-only packet with no enabled production GPU contract is valid; it must not expose a generic test contract as production authority. This resolves the only identified API authorization gap without changing the accepted direct dynamic/lazy behavior.

## Verified design relationships and retained obligations

* `resolve_cuda` is scoped to the live gate, follows healthy-idle first-init/READY accounting, and cannot initialize under an active parent or poison. `complete(cuda_devices=...)` arms a truthful exact initialized tuple before leaf work, completes every listed index on body success/failure while owner exclusion remains held, and never silently substitutes full membership or every available device. An input on GPU with CPU destination still requires its source index. The core cannot inspect the private replay lock or prove a producer's tuple truthful; the producer wrapper and causal controls must do that, as the protocol states.
* `completion_failed()` is an authenticated outcome read inside the gate. A completion error reports first-cause common poison through the live gate; the producer's owner-held `finally` quarantines before releasing its lock. The body exception remains the same object when completion succeeds; distinct body/completion failures remain in order in a `BaseExceptionGroup` with continued attempts for other declared indices. Bootstrap `report_failure` needs no fabricated operation and cannot heal poison. The protocol's misuse and escaped-gate refusals prevent a successful result from an unfinished completion scope.
* A successful local gate changes no core generation/revision/currency. Replay mutation must advance its own revision and install must check that owner revision plus the original core token and issuer-held material. A local gate cannot authorize sample/prepare/install, arbitrary callback purity or post-poison CUDA initialization. Public healthy GPU routes may not be migrated to disabled contracts and called complete; later source qualification must enable the exact supported route. CPU/scratch current behavior remains admitted. The new nested preflight inventory condition does not prove any old supported dynamic route was removed.

After the single binding clarification, the local-gate protocol is suitable as the scoped public API handoff to a fresh bounded core author. Its CPU controlled seams establish protocol behavior only. Source-qualified leaf classification, actual Torch initialized-query/initialization effects, asynchronous owner exclusion and one/two-device CUDA execution remain the accepted later evidence gates. No B6 completion, release or accounting change follows.
