## Exact typed public API

All listed arguments are required; none has a default. Context-manager return types below describe the public callable, not an undecorated generator implementation.

- `AmbientRNGDomain.local_cuda_access(*, participant: RNGParticipant, contract: LocalCUDAContract) -> AbstractContextManager[LocalCUDAGate]`
- `LocalCUDAGate.resolve_cuda(*, device: torch.device) -> int`
- `LocalCUDAGate.complete(*, cuda_devices: tuple[int, ...]) -> AbstractContextManager[None]`
- `LocalCUDAGate.completion_failed() -> bool`
- `LocalCUDAGate.report_failure(*, error: BaseException) -> None`

`LocalCUDAContract` and `LocalCUDAGate` are opaque, nonportable, noncopyable identities with no public constructor/reinitializer or writable authority slots. A contract is a source-issued classification capability, not an RNGOperation or membership. A gate is a short-lived authenticated synchronization capability, not permission to draw, prepare or publish. `complete` is deliberately a context manager surrounding the actual local work; it cannot be replaced by a caller claim that completion already happened.

## Source-issued classification, not caller-declared purity

The core owner maintains an internal immutable contract manifest. Each issued contract identity maps to one exact producer entrypoint/path, its supported ordinary tensor/DTO input class, its ambient-free rationale, whether healthy local use is admitted, and whether READY post-poison use is qualified. The manifest is maintained by reviewed source changes; no public registration, boolean `ambient_free`, arbitrary entrypoint string, evidence-path string or caller-created contract can add authority. It is separate from the existing RNG entrypoint membership set. A valid `RNGParticipant` does not itself qualify a local leaf.

The manifest's qualified production contracts are exported as named opaque constants by the owning producer/core API capsule; their names must identify the concrete audited path. Adding an entry requires source-owner review of the actual algorithm and input restrictions, and the relevant supplier/qualification evidence. Do not invent a broad `ALL_REPLAY`, `TENSOR_WORK` or arbitrary callback contract. Several concrete entrypoints may share an internal implementation, but each exported contract records its actual admitted route; unsupported subclasses/custom callbacks cannot inherit ambient-free status merely by passing that constant. Producer dispatch is responsible for invoking only the recorded path with its supported inputs, just as existing membership cannot prove arbitrary caller code obeys its declared devices.

The initial core-only writer may implement this mechanism with **no enabled production GPU contract**: current capsules do not yet establish a particular GPU local leaf's complete post-poison contract. It must not fabricate qualifying constants from CPU tests or add an all-purpose compatibility contract. Its focused CPU protocol tests may use a controlled internal manifest fixture with a clearly test-only finite leaf entry; that seam is not a public issuer and must not enable any production path. Such tests validate the real gate/capability machinery, not GPU purity. A later bounded replay/supplier packet publishes and enables the precise source-issued constants needed by its real routes, distinguishing healthy-use admission from post-poison qualification.

This is staged implementation, not a deployable replacement that silently rejects supported ordinary replay operations. Do not migrate/ship an existing healthy direct GPU route to a disabled contract and declare B6 complete. Its producer contract must be established before that migration is accepted. The already accepted conservative gate on unproven post-poison GPU leaves remains in force; no historical post-poison initialization guarantee is invented and no user approval is requested on that basis.

## Admission, runtime readiness and scope identity

`local_cuda_access` acquires the sole actual domain RLock before any replay-owner lock, checks the process PID, authenticates the registered participant/live owner and exact issued contract identity, and strongly pins that same lifetime owner until gate exit. It records issuing thread and a unique open scope. Foreign/expired/copied contract identities, unknown participants, dead owners and wrong-process use refuse before leaf work. Contracts belong to the actual source issuer/domain policy; a caller cannot rebind them to a different manifest record. A contract identifies the producer route, while the participant identifies the concrete lifetime owner whose wrapper is responsible for that route.

Healthy custody requires the contract's healthy-use admission. Common poison additionally requires its individually qualified post-poison permission and a READY runtime already established during healthy custody. A merely initialized-looking runtime is not newly verified after poison. Unknown readiness or an unqualified leaf refuses before the leaf body and before initialization/verification. CPU-only leaves do not call this API: they retain the existing owner-only path and no CUDA attribute access.

A healthy idle gate's `resolve_cuda` follows FIX1's structural checks, first-init currency invalidation, READY verification and failure states. An active parent prohibits initialization; a poisoned gate prohibits initialization and unknown-runtime verification. Already READY resolution re-reads actual current selection for unindexed CUDA only under the contract's supported initialized-query conditions; never permanently pin `cuda`. No gate enrollment API exists. A local gate does not register/update membership or create an operation token. Ambient-free local completion need not be a subset of RNG membership: it covers its actual initialized tensor devices, while later `device_operation` must still idle-enroll and validate its own complete subset. Do not confuse runtime readiness, local completion, and RNG enrollment.

The local gate may operate inside a real same-thread parent operation because it admits only the qualified ambient-free leaf and never grants/invents lineage. It does not let a public sample/prepare/install omit required lineage. It cannot bootstrap or enroll under that parent. Reentry during bootstrap and unrelated same-owner lifecycle callbacks remain forbidden. Internal local helpers reuse their producer's existing gate and completion scope; they do not open a second gate from inside an independently acquired owner-only lock.

Every public gate method verifies exact open scope, issuing thread, PID and continuing actual-domain ownership before acting. Completion callbacks cannot retain the capability beyond the synchronous scope. No await/task handoff is allowed. Gate pinning extends through owner-held completion and exception processing; normal parent-operation pins do not replace this earlier protection. `completion_failed` is authenticated outcome inspection only, not admission/currentness authority and not a `domain.status` call.

## Completion ordering and producer obligations

The required healthy local sequence is:

1. Enter the participant/contract-bound local gate, resolving/initializing a needed destination under healthy idle custody **before** acquiring owner exclusion.
2. Acquire that owner's replay RLock, check local health, and inspect supported input/retained/output-plan metadata. Compute the exact sorted unique initialized CUDA indices for all source, destination and temporary work. Read the current effective selector at the actual supported operation boundary; do not replace public `self.device`. No CUDA tensor work is permitted before this inventory and completion scope are established.
3. Enter `gate.complete(cuda_devices=actual_tuple)` **inside the owner lock**. Entry validates exact tuple shape, initialized bounds and the contract's readiness conditions without starting CUDA initialization. It arms completion for that tuple before yielding. It must not infer all-device coverage or guess an index. `()` is permitted for an authentically selected no-device branch and invokes no CUDA completion, but callers with genuinely CPU-only leaves should remain on their existing owner-only path.
4. Execute only the contract's actual local leaf. Apply producer owner-revision discipline before a mutation body. Internal helpers share the same effective-device/completion scope; a helper cannot add an unlisted device after work starts. If the algorithm needs another device, inventory it before entry or use a separately planned next local scope after the first has completed; never retroactively bless an incomplete tuple.
5. Exit `complete`, performing real completion of every declared index while owner exclusion still holds. In an owner-held `finally`, inspect `gate.completion_failed()` and quarantine the affected replay owner when true, preserving/incrementing its revision as required by existing quarantine discipline. Complete this quarantine before releasing the owner lock. Then release the owner lock and finally the local gate/pin.

The public core cannot prove that a producer holds its private owner lock or has listed truthful devices. That obligation remains in the concrete producer wrapper and must be verified by its actual source and causal test. `complete`'s context nesting makes the required lifetime expressible without a private lock or core helper bypass. A gate supports one outer completion scope per local invocation; repeated or overlapping `complete` entry refuses. Known internal helper calls reuse the already armed scope. Calling `resolve_cuda` during armed leaf work, using `report_failure` as a success signal, or escaping the gate does not authorize more work.

A gate may exit before `complete` was entered when structural validation/health checks refused before any leaf work; this is not a completion failure or automatic poison. A gate that entered completion cannot leave with an active unfinished completion scope. Normal structured use exits it first; misuse refuses and cannot return a successful local result. Completion must run on body exceptions as well as success. A returned local result is not delivered to the caller until completion and owner-held quarantine processing finish.

## Failure identity, poison and currentness

`complete` captures a body exception without replacing its identity, then attempts `torch.cuda.synchronize(index)` for **each** declared index in stable order while holding the gate and owner lock. A failure on one index must not skip attempting the remaining declared indices. It never synchronizes undeclared available/historical devices. Record each distinct completion exception, set the gate's failed-completion marker, and report the first completion failure through the authentic gate's `report_failure`. Existing common poison retains its first cause; neither local access nor reporting heals or replaces it.

If completion succeeds, re-raise a body failure unchanged, or return normally. If completion alone fails once, raise that original exception. If the body and completion fail, or multiple distinct completion failures occur, raise a BaseExceptionGroup retaining the original body exception first and each distinct completion exception in completion order. Do not duplicate the same exception object. Ordinary argument/leaf-body failure with successful completion does not itself imply common poison or publication corruption. Producer partial-publication quarantine remains independent and mandatory where applicable. CUDA completion uncertainty always triggers the owner-held quarantine step even if the body had already raised.

`report_failure` remains available on both accepted gate types for pre-operation bootstrap uncertainty; local `complete` calls it automatically for completion uncertainty. Its public use neither sets a successful completion marker nor consumes/refreshes a prepared token. Bootstrap failures follow FIX1 exactly: first actual attempt invalidates prior currency once, failure is conservatively poisoned, and successful init followed by ordinary invalid-index refusal remains READY with that invalidation. No owner data corruption is asserted merely because initialization failed before the owner body.

Successful local work does not increment core operation revision/currency or membership generation merely through this gate. Local mutations advance the replay owner's revision under its lock; final install checks that owner revision and original issuer-held material in addition to its genuine core token. Gate outcome inspection is not a substitute currentness check. Completion failure may poison an active parent's domain; its later outer exit retains normal operation cleanup, never grants success through the local route, and must not duplicate an already propagated exception merely because it was also the retained poison cause.

## Finite CPU protocol obligations and hardware boundary

Use the core writer's existing two-body <=2400-line packet and internal controlled manifest/CUDA seams; add no hidden source body. The finite controls are:

- Exact required API signatures and opaque identities; arbitrary strings/booleans/fabricated/foreign contracts fail; no public contract issuer; production unqualified contract cannot be enabled by caller assertion. Distinguish healthy-only from READY post-poison fixture permissions.
- Real participant pin survives dropped external references through gate and completion; expired/cross-thread/wrong-PID gate methods refuse. A competing thread blocks at the actual shared domain. Active-parent local access grants no RNGOperation/lineage or active enrollment/bootstrap.
- Poisoned unknown-runtime and healthy-only contracts refuse before init/verification/body; READY qualified fixture admits only its finite local path. CPU/disposable-scratch producer leaves remain outside this mechanism and do not acquire new CUDA prerequisites.
- Genuine `complete` scope yields only after tuple validation; synchronizes exact listed indices on success and body failure; empty tuple performs zero CUDA completion queries; malformed/out-of-range tuples fail before body; no all-device or membership-expansion side effect. Repeated/overlapping/escaped scopes refuse.
- Body failure with successful completion preserves exception identity and healthy state. One/multiple completion failures, with/without body failure, preserve identity/order and attempt remaining declared devices; first-cause poison persists. Outcome marker is authentic and remains readable inside the gate for owner-held quarantine; expired outcome reads refuse.
- A real owner-lock fixture wraps `complete`; a competing mutation cannot proceed until synchronization and failed-completion quarantine finish. Internal helper reuse cannot bypass its armed inventory. Same-parent local mutation invalidates by owner revision, not a fabricated core currency change; no-op local read preserves it.

These CPU tests establish protocol causality only. Enabling actual production GPU leaf constants, initialized-runtime query effects, CUDA RNG preservation, multi-device completion and asynchronous same-owner exclusion require the separately bounded source/supplier evidence and real hardware controls already specified. No hardware pass, final B6 acceptance, capability-removal permission or new scope waiver is granted here. No genuine additional owner decision is presently required: the missing API is specified within the accepted gate/finite-leaf rules; any later demonstrated unsupported route must be raised with concrete evidence rather than silently removed.
