## One finite finding

**S1/Q1 — do not make the current generic completion tail a new outcome API contract.** The “Exact attribution and completion rules” paragraph mandates sorted short-circuit stopping and forbids all-device attempts; causal test3 additionally requires exactly0,1 with no2. Current `_complete` does stop on its first synchronization exception, and this outcome packet should preserve its current implementation. But root's explicit accepted ruling also says not to promote that exact early-stop suffix into a required public API/test or expand/restrict generic cleanup solely for this addition. The proposal currently does promote it. This is a finite contract/test overconstraint, not a defect in per-invocation attribution.

Required amendment: keep one invocation attached to the existing actual completion phase and preserve the existing shared operation implementation. Do not add a receipt-driven retry or second pass. Remove the permanent “no2”/mandatory unvisited-tail assertion and any wording that independently fixes generic early-stop semantics as part of the outcome capability. Local completion's already accepted all-declared-devices-after-error requirement remains unchanged.

Concrete replacement for the overconstrained paragraph:

> Preserve the existing generic operation completion implementation in this packet. The receipt observes that invocation's actual required completion phase; it introduces no retry, second synchronization pass or alternate cleanup policy. A synchronization exception or unfinished required phase seals True. The current generic implementation stops on its first synchronization error, which is a source fact rather than a new public outcome guarantee about an unvisited tail. Any later generic cleanup change requires its own justification and must preserve the receipt's phase attribution. Local completion continues to follow its separate all-declared-devices requirement.

Concrete replacement for causal test3:

> For declared devices(0,1,2), inject a failure at1 and prove this invocation's actual completion phase failed, True was sealed before exception handling/owner unlock, and existing exception/union behavior is retained. Compare completion events with the existing device_operation under the same controlled schedule; do not independently require that2 remain unvisited as a permanent outcome contract. A successful(0,1,2) phase reads False. Body-only failure still runs the existing required completion phase. The new receipt itself adds no synchronization/retry.

These replacements leave the current source behavior intact and require no generic cleanup expansion. Root can adopt this finite normative correction or obtain the designer's amended record before implementation. The immutable reviewed proposal itself was not edited.

## Assessment of the chosen surface

- **Exact API and source issuance:** `device_invocation` has the same four required explicit device-operation arguments and returns a distinct opaque single-use `RNGDeviceInvocation`. Context entry yields the existing authentic `RNGOperation`; there is no public operation getter, issuer, completion callback, policy registrar, full-member adapter or optional/default path. Entry rechecks actual domain/member/lineage/poison/device state after lazy issuance. This is a meaningful additional capability rather than omission compatibility.
- **Standalone lifetime:** immutable outcome belongs to the issued context, so it need not authenticate an already retired operation. Issued/entering/active/entry-failed states cannot claim False. Sealing before the wrapper receives any exit exception makes the owner-held `finally` usable for actual standalone completion uncertainty. Historical reads remain evidence only and do not revive lineage, membership, tokens or publication authority.
- **Nested attribution:** distinct invocation handles can yield the same authentic parent lineage without sharing their own completion result. Nested results describe that scope's own subset completion; an outermost result describes its own final accumulated union. A descendant error/common poison cannot by itself set another scope's marker. The explicit outer-union caveat prevents a receipt from pretending to identify one owner's failing device. A poison-refused later sibling remains entry-failed with no outcome.
- **PID/thread/authentication:** exact issuer/type/weak-registry authentication, actual PID first and issuing thread-object identity address forgery, fork inheritance and recycled numeric IDs. Outcome reads avoid domain/owner locks and CUDA and remain usable after poison. The proposed inherited-process and wrong-thread controls must later prove those orders at actual method entry, including context entry/exit.
- **Pins and stable evidence:** weak identity registration with no value-to-key strong cycle and clearing owner/operation/generator/exception/traceback/closure execution references at termination are sufficient design requirements to avoid completed-handle leaks. Thread-object identity and no-transitive-owner-retention must both be honored by the eventual representation; source/weak-reference tests must verify that actual implementation. This proposal does not yet supply implementation proof.
- **Exceptions/currentness:** marking at the actual completion call site independently of the failures list preserves the bodyE versus body+syncE distinction after deduplication. LiteralFalse/no suppression and existing aggregation preserve outward identities. Shared underlying operation semantics retain currentness, pins, revisions and outer union rather than recreating lineage. False cannot heal poison or override independent restoration/publication quarantine.
- **Producer quarantine usability:** the wrapper's entered flag avoids querying an entry-failed context; its owner-held post-exit inspection can distinguish completion uncertainty before owner release. Admission-before-owner order and the actual producer quarantine transition remain separately reviewed producer obligations. The core-only fixture cannot claim actual producer integration or arbitrary owner-lock detection.
