## Decision proposed

The outer POP boundary wrapper is the sole consumer of **its own** `RNGDeviceInvocation` outcome. It retains real parent mutation exclusion and the relevant preflight child-owner locks through outer completion, reads the sealed outcome, and commits the justified owner health transition before releasing those locks or returning a healthy result. The replay child wrapper remains responsible for its own invocation outcome; core does not make owner policy decisions.

For the ordinary flat/PER routes proven by the alias capsule, successful child completion followed by failed outer completion means:

1. The parent becomes unusable for normal guarded work and healthy snapshot/publication, because its Q/target/gradient/optimizer, tensor and related logical state cannot be certified as one successful parent operation.
2. The successful child's receipt remains False. Replay is **not** marked owner-uncertain merely because it participated, its device appears in the outer union, or common domain poison is set.
3. Existing domain poison remains in force. Leaving replay's owner-local health unchanged does not permit ambient work forbidden by that poison, clear the poison, or qualify an unreviewed local-after-poison route.

A minimal monotonic parent owner-health state is required: healthy -> uncertain on actual parent completion uncertainty. Its concrete field/name is an implementation choice; it must be owned by real parent exclusion, not inferred from `_step_active`, a vector record that has already been cleared, or exception shape. This proposal does not introduce rollback, recovery, an all-owner health registry or a new public quarantine API. Existing separately justified body/restoration/publication failures can also leave the parent unusable; a False completion receipt must never heal those failures.

Alternatives rejected: making the replay child consume the later parent result misattributes phase ownership; quarantining all child owners confuses shared-device uncertainty with actual effects on those owners. An exception-based parent catch cannot distinguish clean body E from body-plus-sync E after identity deduplication. The adopted per-invocation receipt supplies the needed distinction without a new core API.

## Why copied outputs change the replay response

The parent capsule establishes that Q/target forward, backward, optimizer/scheduler and target copying occur after sample_batch returns. The flat/PER capsule establishes that ordinary typed ReplayBatch tensor fields are detached clones, receipt arrays are copied, and normal push inputs, serialized transports, validated DTOs and prepared publication stages do not retain live replay aliases. A parent using those returned tensors reaches batch-owned allocations, not live replay columns or issuer-held prepared storage.

That is enough to exclude the stated **normal returned-batch alias path** from replay-specific quarantine. It does not prove parent CUDA success, arbitrary raw-alias safety, recurrent ownership, completeness of future inventories, or Tensor-subclass behavior. PER's untyped sample relies on ordinary advanced indexing, not an explicit clone; do not strengthen that supplier claim. Inputs still require caller quiescence until their copy/completion boundary.

Later priority updates, pushes or installs are distinct replay invocations. Each wrapper consumes its own outcome under that replay owner's lock. If such a later child is uncertain, its own replay health transition is justified independently of the earlier successful sample. The parent must not treat the first successful child receipt as a lifetime certificate for subsequent replay calls.

## Exact parent boundary and success cut

The parent wrapper uses the adopted required-argument `device_invocation` surface with its authentic participant, operation kind, supplied lineage and inventoried CUDA devices. No manually fabricated lineage or diagnostic status is accepted. The parent participant, lock, finite entrypoint coverage and device inventory must be implemented and verified in the bounded parent packet; the current parent capsule explicitly says these mechanisms do not exist at the inspected bytes.

The wrapper's success cut is **after** exit completion and outcome inspection while parent exclusion is retained. Constructed result objects, counters, vector progress, metrics or checkpoints must not become a healthy returned/published result before that cut. Internal CPU assignments may already have occurred: no automatic rollback is promised. If completion fails, mark the parent uncertain even if `_vector_steps` was cleared or `_step_active` would otherwise be reset. Do not make a completion response conditional on an extant vector record.

While uncertain, covered public parent mutation, learning, selectors and healthy snapshot/checkpoint publication must refuse before new effects; previously captured raw Q/optimizer/reference access remains outside guarded-entrypoint enforcement. Read-only failure diagnostics are not healthy snapshots. This proposal supplies no new recovery permission. A fresh instance or separately accepted recovery path is a distinct future contract.

The actual consumer flow is: establish existing approved admission and owner custody; create the parent's fresh invocation; enter and perform existing work with its genuine lineage; exit; if entry succeeded, read this invocation's completion outcome in the wrapper's unconditional finally; if True, perform the non-CUDA parent owner-health transition and any separately justified exact child-owner transitions; only then unwind owner locks. The entered flag distinguishes failed entry from an entered operation. Preserve exceptions; the health transition must not call user code, await, issue CUDA work, acquire an out-of-order owner lock, or fail in a way that replaces the primary error. Unexpected inability to establish the fail-closed state is a material implementation failure, not a reason to return normally.

Clean body E plus successful completion yields False and follows existing body-error policy. Body E plus synchronization failure with the same E yields True and marks the parent uncertain even though the outward error is still exactly E. Distinct failures retain the established aggregate identities/order. No inference from group presence or poison is used. If entry itself fails, no result exists to inspect and no body has run; preserve entry failure handling rather than inventing a completed parent outcome.

## Custody lifetime and lock order

Maintain the established common admission-before-owner acquisition discipline. Resolve idle/bootstrap requirements before starting an active parent operation; no child initializes CUDA inside that operation. Preflight identifies the exact participating owners and required device work before the body. All parent/child mutation locks needed for this boundary are acquired in the parent packet's explicit deterministic global order and retained through completion/outcome consumption. Reentrant nested helpers reuse those locks and genuine lineage; they do not invert the order. No new unrelated owner is discovered and locked opportunistically while handling an exit failure.

Do not place owner locks inside a context that releases them before outer invocation `__exit__`. The receipt read and fail-closed transition themselves acquire neither the domain lock nor new owner locks. Release covered child locks and then unwind the remaining acquisition stack only after these decisions. Exact parent/ENV/runtime/child ordering is a required supplier/integration fact still missing here; the above constraints do not invent its concrete order.

A wrapper nested under a larger parent invocation consumes its own phase only. If a still-larger scope may enqueue effects on the same actual owner afterward, that larger scope must retain the relevant owner exclusion and consume its own later outcome before final release. This handoff must terminate at the actual outer effect owner; a local child success never certifies a future ancestor phase.

## Raw replay-owner aliases: finite support boundary

The exposed replay object and public row columns/PER arrays allow raw references. Normal batch copies do not erase that separate reachability. The currently evidenced parent learning path does not establish post-child raw replay-column use; therefore the ordinary contract above does not add raw mutation support or change existing caller-owned quiescence into an imagined detector.

If a bounded parent route intentionally supports subsequent CUDA work through a raw live replay tensor alias, it must explicitly identify the concrete replay owner **before** that work and retain that owner's existing preflight lock through the outer phase. Its source-reviewed route must establish storage reachability and the actual effects/inventory; arbitrary pointer scanning, callback declarations or a public policy registrar are not substitutes. A plain CPU PER array reference alone is not evidence of CUDA effects, though CPU mutation can independently require owner consistency handling.

For such an explicitly supported raw route, an outer True plus established actual post-child CUDA access to that owner's live storage leaves that owner's covered state uncertified. The parent consumer must request that exact owner's producer-owned uncertainty transition while its lock is still held. This is a proposed semantic obligation, not an invented callable: the supplier must provide the finite authenticated integration mechanism and its lock/authentication preconditions before the route can be admitted. Do not read/write replay private status from the parent as an implementation shortcut.

The implicated set is the source-established actual owners exposed to uncompleted post-child effects, not every replay participant or every owner on the same device. Because the receipt does not identify a failing device, it cannot narrow uncertainty among several actually exposed owners by guessing which kernel failed. Conversely, absence of an established raw effect for another owner forbids adding it merely through common poison. Even a read-only raw CUDA access needs completion/exclusion reasoning before its owner can be released for mutation; source-specific proof can justify a narrower response, but is not supplied here. No per-device receipt or blanket all-owner rule is proposed.

Raw aliases used concurrently outside cooperative exclusion remain the caller-quiescence limitation. This design does not promise to detect them, guard arbitrary Python access or make an unguarded external write safe. Any implementation claiming raw-route support must supply the preceding evidence and tests; until then that claim remains unqualified, without blocking ordinary copied-batch or independent constructor/CPU work.

## Finite executable acceptance cases

These cases belong to the bounded parent integration packet, with existing producer/core controls reused. Stand-ins can prove causal plumbing; they do not qualify CUDA hardware effects.

1. **Copied batch / parent failure:** flat and PER typed sample completes successfully (child False); parent Q/optimizer work occurs afterward; inject failure in the parent's actual completion phase. Trace shows child completion, parent work, outer failure, parent outcome read, parent uncertain transition, then lock release. Parent covered next step/checkpoint/selector refuses. Replay owner-local health is unchanged; an unrelated replay owner is unchanged. Domain poison still prevents forbidden ambient replay work.
2. **Healthy control:** same participants, devices, copied outputs and effect schedule with successful completion. Child and parent False; no health transition; healthy result becomes visible only after completion and inspection. A blocked competitor observes the post-cut state, never a premature healthy result.
3. **Same-object collision:** compare clean parent body E with successful completion against body E plus outer synchronization E using the same object. Both propagate exact E; only the latter triggers completion-based parent uncertainty. Do not weaken separate existing body-failure policy. Distinct error objects retain ordered aggregation.
4. **Multiple child calls:** successful sample followed by a later failed priority-update/push invocation. The later child True triggers that owner's producer response before unlock; the sample's False is unchanged. A parent phase that subsequently succeeds remains False despite the propagated child error. Preserve parent consistency failure handling without falsely labeling its own completion failed.
5. **No replay alias through normal transport:** use the supplier's ordinary tensor/array profile to establish storage separation for typed batches and the relevant push/transport/restore paths actually used by the parent. Mutating retained parent input/returned batch after successful child completion cannot mutate replay live storage through those paths. Include the actual parent post-sample use, not only a constructor property assertion. No claim for recurrent or custom tensor profiles follows.
6. **Admission and ordering:** barriers show parent and preflight replay locks remain held through outer completion and consumer transition. A contending parent/replay mutation cannot observe intermediate state. Assert agreed acquisition order and no extra acquisition/CUDA call from the failure consumer. Entry refusal executes no body and makes no completion query.
7. **Progress cleanup edge:** simulate a parent body that has finalized its internal vector record and ordinary flags before outer completion fails. The unconditional wrapper still marks the parent uncertain and suppresses healthy result publication; no reliance on retained vector-progress records.
8. **Raw-route conditional test:** only if such support is proposed, enqueue a controlled post-child effect through an explicitly tracked live replay alias while its owner lock is held. Child False then outer True must trigger the designated exact replay-owner transition before release, together with parent uncertainty. A copied-batch-only owner and an unrelated same-device owner remain unchanged. Successful outer completion makes no completion-based transition. A route without the authenticated owner transition/lock facts cannot claim this test passed by directly editing private health.
9. **Nested outer handoff:** a local parent phase succeeds, then a larger owning invocation fails completion while the relevant locks remain held. The larger designated consumer handles its actual effects; earlier receipts remain immutable. Verify the final release belongs to the true outer effect boundary.
10. **Inventory and rejected work:** parent and child inventories cover actual queued prefix work, including failure paths and copied-source devices, using the appropriate producer's already established traversal/order rules. A rejected no-work path must not cause arbitrary initialization. Do not expand generic completion order into a permanent tail-visitation contract; compare with the shared existing implementation and preserve the separate local all-declared-devices rule.

## Facts still needed before parent implementation/acceptance

The capsules settle the normal flat/PER copied-output distinction and identify the parent as the consumer. They do not supply the current parent participant/lock implementation (none exists at the inspected source), exact finite guarded entrypoints and outer boundaries, concrete parent/ENV/runtime/child lock order, or actual device inventories for every Q/target/optimizer/restore path. Those are mandatory bounded parent packet work, not reasons to reread additional bodies in this reviewer context.

Recurrent returned/stored ownership remains unsupplied. Do not apply the flat/PER alias conclusion to it. Whether any real supported parent path performs later raw replay access must be established by its owner; the capsules do not prove such a path exists. An authenticated producer mechanism for parent-triggered exact replay-owner uncertainty is needed only if that raw-route support is claimed; no public mechanism is invented here. Exact recovery policy remains out of scope and cannot be inferred from a historical False receipt.

The adopted outcome API still needs its separately reviewed implementation and qualification before dependent CUDA integration can ship. Parent caller lineage integration, actual owner-lock transitions and real CUDA hardware checks remain required. This proposal does not block independent A/B constructor/CPU work, qualify B6 producer integration, or close any package/programme gate.
