## Execution isolation and allocation boundary

Use one existing checkout and one reviewed source snapshot; no multiplied branches/worktrees or per-worker source copies. Independent spawned test processes may execute that snapshot concurrently when root has assigned devices and confirmed memory headroom. They have separate process-domain/RNG identities, but sharing a physical GPU still shares scheduling and memory pressure. Do not equate process isolation with GPU timing isolation.

First-initialization controls require genuinely fresh processes. A worker pool reusing an already initialized process cannot run them honestly. Poison controls require disposable processes; neither public poison nor CUDA uncertainty may be cleared to recycle the child. Do not use fork to inherit an established process domain/CUDA runtime. Same-parent lineage and same-owner exclusion schedules remain synchronous issuing-thread protocols with only the explicitly coordinated competitor thread.

Root should reserve the GPU(s) for H7/H10 timing/exclusion windows and run ordinary independent cases elsewhere or afterward. Do not launch sixteen GPU cases simply because sixteen CPU workers are promised. Two-device cases require two visible GPUs in the **same process**, sufficient per-device memory and recorded logical-index mapping. **One GPU cannot qualify two-device dynamic selection, retention, union or exclusion.** No GPU allocation is made by this preparation record.

## Exact-source receipts and portable checkpoints

At actual run time, root records the measured CPU/RAM/GPU resources, visible-device mapping, GPU model/driver, Torch/CUDA versions, process-start method and relevant environment, plus exact SHA256 for every implementation/test artifact in the executed packet. Record test selection, seed/fixture identity, process identity/role, exit status and raw evidence artifact hashes. Distinguish real CUDA execution, controlled fault injection, simulated CPU seams, SKIP and UNRUN per case. Earlier design/source hashes identify planning evidence only; they are not substitutes for future executed-byte hashes.

Checkpoints used for cross-process/server continuation must be ordinary supported serialized data with their format/source provenance and content hashes. Never serialize or transfer participants, operations, current tokens, local contracts/gates, owner locks or prepared publication authority. Reconstruct fresh lifetime owners and lawful membership on the destination, then validate/materialize through the destination's real API and explicit lineage. A copied checkpoint does not carry CUDA enrollment, READY state, poison recovery or hardware qualification. Record actual device mapping on reload rather than treating source-machine ordinals as portable hardware identity.

If source changes after a receipt, that receipt remains evidence for its recorded bytes only; root identifies the affected checks to rerun. Keep successful CPU protocol evidence distinct from final real-device receipts. No checkpoint or future server promise upgrades UNRUN to PASS.
