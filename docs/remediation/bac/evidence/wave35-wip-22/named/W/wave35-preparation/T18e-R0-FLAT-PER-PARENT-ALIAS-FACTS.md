## Supplied push and priority-update inputs are not retained aliases

Both push paths first validate inputs, construct ordinary placeholder/presence temporaries as needed, and produce moved values with value.detach().to(self.device).clone() (F262 onward, P483 onward). Even when to returns the same device object/storage, clone creates independent moved storage. New persistent columns use torch.zeros; existing columns are reused. Indexed assignment copies moved values into those persistent columns. The supplied observations/actions/RewardTensor total and optional components/next_observations/dones/masks are not installed directly as owner columns. The recorded-mask route follows this same ownership boundary.

Consequently, after successful completion of the correctly inventoried push, later parent mutation of its original observation/reward/mask references does not mutate the retained replay through those original input aliases. Inputs must still remain quiescent through validation/copy/completion; asynchronous completion correctness is not established by source copying alone. Existing raw owner tensor aliases are a distinct case below.

P._prepare_priority_update (P669) detaches/converts td_errors to CPU float64 and obtains a NumPy view of that temporary. For an already CPU float64 input this can share caller storage transiently, but the implementation only reads it to calculate fresh candidate priorities; it stores neither that input/view nor the input indices. It copies self.priorities, mutates the copied array, and publishes that array plus a scalar maximum. Both stable-ID and physical-index public methods therefore retain no td_errors/indices alias. The conversion can touch a CUDA source before an invalid ID is discovered; completion coverage must include that work.

## Serialization, validation and prepared publication ownership

F.serialize (F443) slices or concatenates live rows, then detach().cpu().clone(); P.serialize (P759) likewise copies each returned nonempty tensor to owned CPU storage. PER priorities/unit_ids use copy, and sampling metadata deep-copies its engine state. Empty columns yield None. Scalar geometry/counters/modes are ordinary immutable values. Neither serialized tensor/array transport aliases live storage under the ordinary profile.

Historical serialization/property/install paths use _record, _archive_from_state and each family's _own_archive/_merge_archives. The sealed helper capsules establish recursive ownership copying of ordinary archive containers/tensors and clone-on-read for original_state/source_formats. Thus returned historical archives/records do not expose installed archive storage through normal public access. The supplier's internal direct-slot metadata mechanism is not a public returned alias, and a future inventory must not make it one.

Both _require_tensor implementations validate tensor type/dtype/shape, perform applicable finite checks, then return value.detach().clone() (F473/P813). Validated DTO tensor fields are owned copies of transport inputs. PER arrays and sampler state are also copied/reconstructed. Legacy-state mappings and archive values are owned through the supplied history graph. These DTOs remain mutable through their contained tensors/containers; they are data, not restore authority.

Materialization (F620/P1030) first clones the legacy payload or reconstructed current DTO mapping, reruns complete destination/content validation, then creates independent destination allocations and copies validated row data into them. Archives are merged through ownership copies; PER priorities/unit_ids and sampler are copied/reconstructed. The replay_prepare decorator returns only an identity-only PreparedReplay (C163), retaining material in its issuer registry (C88). The public handle has only a weak-reference slot, no material getter and no material-taking constructor; normal parent access to the handle exposes no candidate tensor or array.

load_prepared (F692/P1120) stages fresh detached tensor clones of candidate storage; PER also copies priorities/unit_ids and reconstructs its sampler. It merges owned archives, validates the original owner revision/token immediately before publication, then installs staged references and consumes the handle. Installed live storage therefore does not alias its original transport, validation DTO or issuer-held candidate. A parent retaining any of those public earlier objects cannot enqueue a write to installed replay storage through that normal chain.

## Actual remaining alias reachability and parent implication

Both replay classes expose public row Tensor attributes, and PER exposes priorities and unit_ids NumPy arrays. A caller holding the replay object can read those attributes directly, retain an alias/view or replace them. C's private registry/locks are also implementation attributes, not a hostile-Python sandbox. These raw accesses are outside the guarded transport ownership guarantee and retain the existing cooperative quiescence obligation.

A parent with a raw replay Tensor alias can enqueue reads/writes of actual replay-owned storage after any earlier child return. A parent later calling push/update/sample/install reaches replay again through a new producer invocation, whose own effects/inventory/outcome must be attributed separately. An ordinary batch/receipt/serialized mapping/validated DTO/PreparedReplay handle alone provides no such live-storage path in these current flat/PER bodies.

The supplied parent capsule establishes later Q/gradient/optimizer work on returned batches but does not establish later raw replay-column access. ## Concrete rejected-input work: inventory must precede actual copies

Rejected input is not generally a no-work branch. The following edges are source-visible and should receive finite A controls:

1. **Validated DTO materialization copies before revalidation.** F620/P1030 call history._clone on state.legacy_state before _validate_serialized. A caller can mutate the returned DTO's ordinary legacy-state dict to add an extra tensor-valued key. The helper capsule establishes recursive mapping-value cloning, so that extra CUDA tensor is cloned before the subsequent exact-key-set refusal. Current DTO reconstruction similarly clones known row-field contents before validating their dtype/shape/content. Inventory cannot use only the finally accepted schema for this clone-before-reject edge.
2. **Embedded archive construction owns before archive content checks.** In a current transport's historical_archives list, replay invokes history._archive_from_state then _own_archive before live-row validation (F487/P838). Supplier facts establish that the canonical archive constructor owns original_state/source_formats through recursive cloning before content/digest validation. A plain record with the accepted outer archive fields but a malformed extra tensor field inside original_state can therefore clone that tensor before nested replay-schema refusal. This statement does not assume the reconstruction helper accepts extra outer record keys; its outer-key rejection order was not established here.
3. **Individual tensor cloning can precede cross-field refusal.** _require_tensor can perform finite reduction and cloning before the caller rejects a device disagreement, invalid action value or later presence/mask relation. Previously processed fields may already have been copied when a later field fails. Include every actual prefix-work source, not only the field named by the final exception.
4. **Stale install can stage before currentness refusal.** Once the handle/material identity exists, load_prepared merges archives and clones candidate columns before _validate_replay rejects stale owner revision/token. Issuer-held source devices must remain inventoried even for this refused install. A foreign/fabricated/consumed handle rejected by _prepared_payload does not reach those copies.
5. **Some schema refusals precede tensor work.** Direct validate_serialized/prepare_serialized on a plain top-level mapping with extra keys hits each family's exact-key-set check before tensor/archive cloning. An unrelated CUDA tensor in that refused extra field must not itself force target initialization or completion. Likewise type/dtype/shape refusal in _require_tensor occurs before its own clone, though earlier fields may already have worked. Do not infer the DTO materialization rule applies to direct raw-transport validation.

The necessary distinction is the actual clone/validation order at each route. A finite metadata traversal for the known recursive ordinary clone input may need to include malformed extra values that will be copied; that is not a generic all-field scan requirement for every route or permission to call arbitrary protocols during inventory.
