## Exact admission and registration rule

`admission(lineage=None)` acquires the real reentrant domain lock (703–706), checks health/busy/local CUDA gate (707–710), and refuses None lineage if an operation is active (711–718). It then **calls `_collect_retired()` at719** before issuing its gate (720–723). A public RNGAdmission is not a LocalCUDAGate, and nested idle admissions are legal. Holding an outer admission does not set the active operation and therefore does not prevent the inner real invocation from exiting to idle and registering its replacement cohort. Other cooperative threads wait on the actual lock; raw aliases and same-thread caller behavior remain caller obligations.

Register requires no active operation or local CUDA gate, drains retirement, and increments generation for the new member (449–480). Unregister has the same idle restriction and increments generation (482–492); adoption requires idle and delegates register/unregister (494–514). Enrollment requires idle, increments generation only for actual inventory expansion, and pins its owner in that admission (832–856). Therefore registration BETWEEN the two preparation invocations is legal under the outer idle admission; registration INSIDE an active outer parent invocation is still forbidden. The proposed ENV scope check must use already-held authority, never enter admission(None) while BANK's operation is active and never infer/adopt active lineage.

Admission enter performs no direct `_revision` or `_currency` increment, but its retirement drain can increment `_generation`. Exit calls `_close_gate` (724–725), which authenticates, deletes the gate and clears pins/owner (688–700): it performs no retirement drain and no direct generation/revision/currency increment. If clearing pins releases a last registered owner, its weak callback can enqueue retirement for the NEXT drain. Plain admission starts with empty pins (721), so exclusion by itself does not pin all registered owners. ENV lock and ENV weak WorldRecord registry actions have no core primitive effect on the supplied facts, but ordinary object lifetime changes can indirectly trigger core owner retirement.

## Exact token arithmetic at the real install

The final BANK token is attributed to the second genuine preparation invocation, after cohort registration and final correlation. `current_token` requires authentic active operation and entered participant and stores `(participant, operation, generation, revision, currency)` (1140–1152). The issuing operation must finish successfully, including completion. Top-level operation exit always advances revision once (1115–1122), even for prepare/validate/install or unchanged RNG bytes. Ordinary kinds also advance currency at entry and exit, and any operation failure advances currency at exit (1107–1118); nested ordinary/failing work has its own currency rule (1066–1091).

Let the token be issued at revision r and currency c. After successful issuer exit the core is at revision r+1, currency c. Its own exit clears active state/pins, drains weak retirement, and only then updates generation on its OWN still-current issued tokens, provided there were no failures and their currency/generation match the pre-drain values (1123–1137). This is existing issuer-exit bookkeeping, not controller refresh. The first preparation invocation's earlier revision and the between-invocation registration generation are already reflected in the final token's issuance. No final token may be replaced to hide later staleness.

The subsequent top-level install operation drains retirement BEFORE binding its participant and authentic operation (1039–1065), but entering kind `install` does not itself advance currency (1107–1109). At `validate_current` INSIDE that actual install, expected participant must have entered, token generation must equal current generation (1162–1165), revision must equal r+1 because this is a different operation (1166–1171), and currency must still equal c (1172–1173). Its own eventual exit revision increment is later and does not invalidate this pre-publication check retroactively. Merely obtaining a device_invocation object is not entering it (922–936 versus956–979). Actual operation entry/exit is what counts.

Consequently, an extra top-level operation between final preparation and install invalidates the token even if called `validate` or `prepare`, even if it draws nothing and preserves every RNG byte. A failure/ordinary nested operation can invalidate currency before exit. Lazy CUDA initialization explicitly increments currency (798–813); new enrollment/registration/retirement changes generation. Device inventory validation (1002–1026) must use truthful previously initialized/enrolled inventory; it cannot silently initialize/enroll inside the install. Health/poison and authentic participant requirements remain mandatory. No shared RNG-state capture, ambient adoption, token synthesis or weakened comparison is implied.

## Pending weak retirement: the decisive condition

A registered owner's weak callback merely queues its participant (471–475). `_collect_retired` does nothing while an operation is active (427–430); while idle it removes each still-dead member and increments GLOBAL generation (431–439). Thus retirement of even an unrelated registered owner can stale BANK's token. Holding a participant handle, token or outer idle gate is not a strong owner pin: members are weak (337–340), the token stores participant/operation rather than an owner (356–362), and admission starts with no pins. Active operation participant owners are pinned (1048–1051,1068–1070,1094–1101) only through its exit cleanup (1123).

Retirement drained by the issuing operation's own successful exit is incorporated into that operation's eligible final tokens (1124–1137). Retirement queued AFTER that normalization and drained by a later idle admission — e.g. ordinary ENV release entry, ENV re-retention entry, runtime/BANK admission — or by install operation entry stales the token. `status()` also drains retirement while idle (1184–1188); it is not a harmless currency witness. Registration/unregistration/local gate entry also have drains (456,489,735). A queued retirement arriving during the active install is not drained by validate_current; the active-operation check defers it until exit. That distinction is the actual currentness semantics, not permission to force collection at a later point or suppress ordinary drains.

Strongly retain the genuine prepared handle/token, replacement cohort and all candidate RNG/native lifetime owners required by the actual producer. Preserve ENV prepared/release records and genuine bound runtime/BANK/ENV/authority owner lifetimes through their required cuts. Supplied BANK record retention of the cohort at BANK1242 is relevant but its sufficiency for the complete reachable owner graph is a producer obligation, not proven by this core read. Additionally, successful install requires **no global membership-changing drain after final issuer normalization and before its validate_current**. Relevant-cohort pinning alone does not guarantee this against unrelated registered-owner GC on another thread: the weak callback queues without the domain mutex. Do not invent a global pin/snapshot API or blanket capability reduction. If unrelated retirement occurs, the existing correct outcome is stale refusal and the owning transaction's failure disposition; unconditional success under arbitrary GC is not established.
