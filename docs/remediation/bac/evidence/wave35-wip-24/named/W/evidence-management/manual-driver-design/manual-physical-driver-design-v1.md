# Genuine manual physical driver: finite design v1

2026-11-14. Design only, pending independent review. No implementation or execution approval is asserted. Author: /root/bac_astra_manual_driver_design. Existing checkout only. All API spellings below are proposed, not existing callables.

## Decision and problem classification

Introduce an ENV-owned manual physical session, composed with the existing independent BANK event API and explicitly local fixture population role. Do not add a second production population/outcome subsystem. This proposes a supported manual physical control capability, not an adapter for an obsolete ENV signature. Preserve the ordinary POP driver and all of its claim, compiled-context, replay, learner and completion checks.

The fixtures incorrectly assumed that arbitrary synthetic BANK contexts and physical ENV decisions share one protocol. They do not. Preserve their useful independent controls, but replace that assumption with explicit composition: physical predecessor/actions/observations and ticks belong to ENV/manual driver; width3/action_dim2 events, sparse event ticks, provider RNG/Adam and admission clocks belong to BANK. No synthetic event is represented as a physical decision, and no physical step earns a curiosity event implicitly.

Two product capability gaps remain after that correction: an authentic complete manual physical step without the POP learning pipeline, and an explicit between-step retirement operation. Both are needed for the supported manual/no-decision behavior retained by approved C2 and the requested B-after-four-steps control. They are not a need for sparse physical clocks, a POP finish escape hatch, or configurable arbitrary claim callbacks.

Alternatives rejected: (1) exposing POP's current post-physics suffix still imposes compiled context, replay, Q and curiosity service; (2) ordinary POP plus a separate replacement BANK adds an unwanted independent curiosity owner and cannot preserve the accepted-parent relationship; (3) changing geometry, forcing dones, fabricating a handle or dropping controls is forbidden. No reduction is recommended. If the new manual or retirement capability is declined, physical-dependent controls remain blocked; their removal requires the user's explicit decision.
