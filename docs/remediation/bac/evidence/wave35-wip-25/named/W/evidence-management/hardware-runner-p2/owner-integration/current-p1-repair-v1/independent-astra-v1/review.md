## Reproduced findings

1. **P2 omits the P1 host-memory consistency check.** P2 `_raw_capacity` (lines 757–769 and derived return) accepts `MemTotal: 1 kB` with `MemAvailable: 10000 kB`. Its parser checks field cardinality and integer conversion but never requires positive total or available <= total. With corresponding host/limited admission facts resealed, the full `Custody` constructor accepts the fixture. P1 `assess_resources` rejects the exact same raw observation with `host memory observation inconsistent` and insufficient-RAM reasons. P1 lines 224–234 and the adopted capsule `raw_to_admission_and_spec.ram` explicitly require this relation. This is a concrete cross-consumer resource-join defect, not merely stricter optional normalization. Add the missing consistency checks and finite regressions before treating P2 as independently reconciling current P1 resource admission.

2. **P2 accepts retained capture storage exceeding its declared overhead.** The full constructor accepts the unmodified current synthetic fixture with actual retained D footprint of 73,728 allocated bytes and 11 inodes (ten files plus directory), while allocation overhead declares 1 scratch byte and 1 scratch inode. P2 `capture_sources` checks the exact ten initial filenames and `capture_boundary` checks inode/references/deadline, but neither compares this retained footprint to overhead. P1 lines 917–922 checks a prepublication projection; that earlier projection is not recorded and cannot honestly be reconstructed from later filesystem state. The appropriate consumer check is the actual postcapture retained footprint under the existing custody boundary, plus the same output/capture/scratch capacity pool join (P1 line 872), not an invented historical footprint. The adopted capsule says these pools must match, and allocation overhead bounds retained capture storage. This witness is a synthetic constructor acceptance only; it does not establish an actual P1 capture exceeded its reservation. Root should coordinate this finite resource check with P4's already required retained-footprint integration.

3. **P1 and P2 accept non-ASCII spellings as actual Linux resource tokens.** Five independent fixtures replace only digits in raw `cpu_max`, `cpuset`, `memory_max`, `memory_current`, or `meminfo` with Arabic-Indic digits. Numeric values, references and derived facts remain coherent. Every full P2 constructor accepts, and P1 `assess_resources` reports no reasons. P2 `_cpus` uses Unicode `\d`, and `_raw_capacity` uses Unicode `.isdigit()`; P1 `cpuset`/`numeric` use `\d`, while its discovery preflight uses `.isdecimal()`. The contract describes these as actual raw `/proc/meminfo` and cgroup controller observations, whose numeric output tokens are ASCII. These spellings cannot be raw values emitted by those Linux interfaces. Restrict the resource-token grammar at those parsing boundaries, preserving legitimate Unicode filesystem paths. This is a finite observation-language defect, not proof that an authentic capture produces such tokens or that a root-approved manifest can be forged.

The findings require independently supplied synthetic authority to reach the consumer, as expected. They do not invalidate the root-pin trust model or show arbitrary same-UID isolation; they show that the consumer's promised structural/resource reconciliation accepts inconsistent authored evidence.
