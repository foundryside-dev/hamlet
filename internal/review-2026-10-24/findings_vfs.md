## New findings (ranked, most severe first)

### F1. Four phases of the closed graph are never executed by `step()` — `apply_modulations`, `compute_rewards`, `emit_observation_features`, `emit_telemetry` — so a VTC write or transition rule scheduled there compiles green, steps green and is silently never applied; action writes at the executed phases after `apply_completion_bonuses` (`apply_passive_depletion`, `apply_threshold_cascades`, `apply_social_residue_effects`, `clamp_and_validate`, `evaluate_terminal_conditions`) compile green and crash on step 1
- severity: P1 (silent no-op) / P2 (compile-green runtime crash)
- where: `step()` requests exactly `phases_through("apply_completion_bonuses")` (`vectorized_env.py:1074`, with actions), `("apply_passive_depletion",)` (`:1080`), `("apply_threshold_cascades",)` (`:1083`), `phases_between("apply_threshold_cascades", "evaluate_terminal_conditions")` = `apply_social_residue_effects`, `clamp_and_validate` (`:1171`, `actions=None`) and `("evaluate_terminal_conditions",)` (`:1176`). `apply_modulations` (graph index 10) and the three phases after `evaluate_terminal_conditions` are never passed to `VTCTransitionRunner.run_phases` (`transition_schedule.py:117-135`); `grep -n apply_modulations src/townlet/environment/*.py` → no hits. `WriteSpec.phase` is any string the graph knows (`vfs/schema.py:299`), and `compile_vtc_*_with_phase_graph` only checks membership.
- failure scenario: `write(public_state, "1.0", phase="compute_rewards")` on ADVANCE → `public_state` stays 0.0 forever; same for a `social_residue` rule at those phases. `phase: apply_passive_depletion` → `ValueError: Transition phase 'apply_passive_depletion' requires actions for VTC action writes` on the first `env.step`.
- reproduction: `probe6.py` → `action write @apply_modulations: compile OK, 2x ADVANCE -> [0.0, 0.0]`, `residue rule @apply_modulations: compile OK, 2 steps -> [0.0, 0.0]`. `probe1.py` D → `phase=compute_rewards: compile OK, 2x ADVANCE -> public_state [0.0, 0.0]`, `phase=emit_telemetry: ... [0.0, 0.0]`, `phase=apply_passive_depletion: compile OK, RUNTIME ValueError ...`, `phase=apply_social_residue_effects: ... RUNTIME ValueError ...`. `probe4.py` B (social_residue rules): `emit_telemetry → [0.0, 0.0]`, `compute_rewards → [0.0, 0.0]`, `clamp_and_validate → [2.0, 2.0]`, `apply_action_effects → [2.0, 2.0]`.
- note: the compiler should refuse any action write whose phase is after `apply_completion_bonuses`, and any rule whose phase the env never executes.

### F2. VTC action writes decide "this target has an agent axis" by `target.shape[0] == num_agents` — a global tensor, zone, group (or pair) variable whose leading extent coincides with `num_agents` is silently masked per agent; any other extent crashes at step; a global scalar target compiles green and crashes
- severity: P1
- where: `src/townlet/vfs/vtc.py:954-962` (`_broadcast_agent_mask`); no compile-time check of target scope in `compile_vtc_affordance_occupancy_with_phase_graph` / `_validate_action_write_targets` (`transition_schedule.py:308-320`, name-only).
- failure scenario: `decl(gvec, global tensor1d [2])` + `write(gvec, "1.0")`; num_agents=2, agent 0 ADVANCE → `gvec [1.0, 0.0]` (row 0 of a *global* tensor written as if it were agent 0's). num_agents=3 → `ValueError: VTC action write 'w_gvec' target leading dimension 2 does not match action batch 3`. Whether a pack runs depends on a training hyperparameter — the exact shape hamlet-f54b887148 described, moved to the write side.
- reproduction: `probe1.py` F: `num_agents=2: gvec [1.0, 0.0] zone_heat [1.0, 0.0]`; `num_agents=3: ValueError ... does not match action batch 3`; `global scalar target: ValueError VTC action write 'w_gscalar' cannot apply a per-agent action mask to scalar variable` (compile was green). `probe2.py` G: group(2) → `grp [1.0, 0.0]`; pair → row 0 fully written at n=2 and n=3 (`[[1,1,1],[0,0,0],[0,0,0]]` — may be intended "source row" semantics for pair, but nothing declares it).
- note: an action write should carry (or infer from the declaration) the target's scope and refuse non-agent scopes at compile.

### F3. `evaluation_mode: eager` evaluates expressions against each static's **compile-time literal**, not its runtime value — an expression over an engine-written global static is permanently wrong
- severity: P1 (authorable, silent, wrong values reach rewards/observations)
- where: `src/townlet/vfs/evaluator.py:184-200` (`if self.mode != EvaluationMode.MARK_AND_SWEEP: context.vfs[var.name] = value` where `value = torch.tensor(var.initial_value)`); `evaluation_mode: Literal["mark_and_sweep","eager"]` is required authored config (`variables_config.py:192`).
- failure scenario: global `gcount` incremented each tick by a transition rule, global `gtwice: gcount * 2.0`, `evaluation_mode: eager` → `gtwice` is 0.0 forever.
- reproduction: `probe2.py` F: eager `t1 gcount 1.0 gtwice 0.0 / t2 2.0 0.0 / t3 3.0 0.0`; identical pack with `mark_and_sweep` → `t2 gcount 2.0 gtwice 2.0 / t3 3.0 4.0`. variables.md documents the mechanism in one clause ("rebuilds static expression context from those literals") without saying the outputs are wrong; `EvaluationMode.EAGER` is annotated "(debug mode)" in code only.
- note: either delete `eager` from the authoring vocabulary or make it read current storage like mark-and-sweep.
